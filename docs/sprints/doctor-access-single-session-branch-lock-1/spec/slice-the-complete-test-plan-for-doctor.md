# SLICE: SLICE: the complete test plan for DOCTOR-ACCESS-SINGLE-SESSION-BRANCH-LOCK-1 — 8 new suites (7 Feature + 1 shared helper file), 6 repinned existing suites, and the exact CI workflow + config edits that make the new suites actually run in both critical-gate variants. Every NEW class/table/flag/permission name below is a proposal inherited from the architect slice and is marked NEW; if the implementer names something differently the test plan follows the implementation, but the ASSERTIONS are not negotiable.

## Decisions
- D1 — THE `sessions` TABLE IS EMPTY IN EVERY TEST RUN, AND THAT SILENTLY DELETES THE FEATURE UNLESS THE TESTS SEED IT. phpunit.xml:30 sets SESSION_DRIVER=array, and both CI jobs set it too (.github/workflows/foundation-evidence-gates.yml:323, :545), while config/session.php:21 defaults to `database` in production. Ruling P3 makes liveness the whole basis of single-session enforcement: an incumbent whose `sessions` row is gone is DEAD and reclaimed, one whose row is alive is DENIED however idle. Under test every incumbent therefore reads DEAD and every 'second login denied' assertion would fail. The table itself exists unconditionally (database/migrations/0001_01_01_000000_create_users_table.php:30-37), so the fix is a test helper that INSERTs the row directly (`daSeedLiveSessionRow`). This imposes a design constraint on the implementation: the liveness probe must read `config('session.table', 'sessions')` rather than a hard-coded name, and must sit behind ONE seam (a single method on the lease service), not be buried in a closure — otherwise the tests cannot express a live incumbent at all.
- D2 — THE LEASE MUST BE KEYED ON A TOKEN IN SESSION DATA, NOT ON `session()->getId()`, AND THE RECORDED SESSION ID MUST BE REFRESHED PER REQUEST. Verified in vendor: `Store::regenerate()` (vendor/laravel/framework/src/Illuminate/Session/Store.php:618-623) calls `migrate()` (:631-642) which only changes the id and leaves attributes untouched, while `invalidate()` (:605-610) flushes attributes first. So a sha256-at-rest token in session data survives all three rotations (AuthenticatedSessionController.php:34, DoctorDeviceSessionService.php:117, DoctorDeviceWebAuthnLoginService.php:353) and dies exactly at teardown — which is the behaviour trap F7 demands and which DoctorDeviceWebAuthnChallengeService.php:133-183 already established for the ceremony nonce. SEPARATELY: because the `Login` event fires inside `Auth::attempt` (LoginRequest.php:45) BEFORE the first regenerate, the session id captured at claim time is stale by one rotation on the password path and three on the WebAuthn path. The liveness probe would look up an id that never reached the store. The middleware must therefore write the CURRENT session id onto the lease when it differs — which is also the throttle (write on change, not every request) that IP5 and finding G16 were reaching for. Pinned by DoctorSingleSessionLeaseTest cases 2 and 3.
- D3 — THE CONCURRENCY ESCAPE HATCH IS A SEPARATE SUITE WITH THE DEFAULT CONNECTION SWAPPED, AND IT SKIPS ON SQLITE. Finding G12 is correct: tests/Pest.php:23 binds RefreshDatabase to every Feature test, so nothing a test writes is visible to a second session and a lock on an invisible row raises nothing — the probe matches zero rows and reports 'not locked' whether or not the lock exists. The verdict's escape hatch already exists twice in this repo: tests/Feature/AccessControl/DailyBranchContextConcurrencyTest.php:59-94 and tests/Feature/LegacyImportHub/LegacyImportHubConcurrencyTest.php:52-110 clone the default connection config into a writer and a probe name, `config()->set('database.default', WRITER)` so the service really COMMITS, use `for update nowait` to turn 'block forever' into an assertable 55P03, and clean their own tables in afterEach. DoctorAccessConcurrencyTest copies that verbatim.
- D4 — DATABASE-LEVEL CARDINALITY INSIDE A RefreshDatabase SUITE MUST USE A NESTED `DB::transaction`. Verified in vendor that this is safe on PostgreSQL: RefreshDatabase holds the outer transaction, so `DB::transaction(fn () => DB::table(...)->insert([...]))` runs at depth 2, and `Connection::performRollBack()` (vendor/laravel/framework/src/Illuminate/Database/Concerns/ManagesTransactions.php:300-313) issues `ROLLBACK TO SAVEPOINT trans2` through `Grammar::compileSavepointRollBack()` (Query/Grammars/Grammar.php:1527-1530) instead of aborting the enclosing transaction, and `transaction()` (:26-76) rethrows once attempts are exhausted. Section M's probe proved the bare form poisons the connection with 25P02 while passing on sqlite. The test must run a FURTHER query immediately after the expectation — that follow-up query, not the expectation, is the actual proof.
- D5 — THE NEW MIDDLEWARE AND SERVICES MUST NOT LIVE UNDER A `DoctorDevice` NAMESPACE. Verified finding G1: tests/Feature/DoctorDevice/DoctorDeviceApiAndNoEnforcementTest.php:245-277 walks every route's `gatherMiddleware()`, skips only `device-api` URIs, and requires any entry whose string CONTAINS `DoctorDevice` to equal `EnsureDoctorDeviceSession::class` — so a globally registered `App\Modules\DoctorDevice\Middleware\EnsureDoctorSessionLease` fails on every web route. Verified finding G2 is survivable either way: the auth-surface scans at DoctorDeviceAccessTest.php:199-245 (which includes bootstrap/app.php at :214) and DoctorDeviceApiAndNoEnforcementTest.php:188-236 use `preg_match_all('/[A-Za-z_]*DoctorDevice[A-Za-z_]*/')`, and backslashes break the character run, so a fully-qualified `App\Modules\DoctorAccess\...` yields NO match while `App\Modules\DoctorDevice\...` yields only the allowlisted bare `DoctorDevice`. Recommended namespace `App\Modules\DoctorAccess`, which also makes `tests/Feature/DoctorAccess/` the honest test location.
- D6 — CLAIM ON THE `Login` EVENT, NEVER IN A LOGIN CONTROLLER, AND THAT IS WHAT KEEPS 3554 `actingAs(` CALL SITES GREEN. Verified section R in vendor: `fireLoginEvent()` is reached from `login()` (SessionGuard.php:573) and from the REMEMBER-ME recaller path (`userFromRecaller()` at :197, `updateSession()` at :200, `fireLoginEvent($user, true)` at :202), while `setUser()` (:996-1005) fires only `fireAuthenticatedEvent`. `actingAs()` → `be()` (Foundation/Testing/Concerns/InteractsWithAuthentication.php:43-55) → `setUser`. So a listener on `Login` covers 100% of production authentication entries — including the recaller a controller-only claim would miss entirely — and 0% of the 3554 `actingAs(` calls across 312 test files. DoctorSingleSessionLeaseTest case 22 is the pin.
- D7 — `DoctorDeviceSessionService::invalidate()` MUST RELEASE THE LEASE, AND THIS IS NOT OPTIONAL. Because `Auth::attempt` at LoginRequest.php:45 fires `Login` BEFORE the gate denial at AuthenticatedSessionController.php:49-95, the password step of a WebAuthn login ALWAYS mints a lease that the gate then abandons at :83. If invalidate() does not release it, the subsequent `Auth::guard('web')->login()` at DoctorDeviceWebAuthnLoginService.php:348 fires `Login` a second time for the same user and is DENIED by the doctor's own orphan — no doctor could ever complete a WebAuthn login. It would also flip the error key at tests/Feature/DoctorDeviceWebAuthn/DoctorPwaWebAuthnTest.php:541 from `credential` to `email`, which is migration cost E7. Pinned by DoctorSingleSessionLeaseTest cases 17 and 18 and by the added assertion in that existing test.
- D8 — THE DENY PATH USES `logoutCurrentDevice()`, NEVER `logout()`. Verified: `logout()` (SessionGuard.php:650) calls `cycleRememberToken($user)` at :657; `logoutCurrentDevice()` (:680) does not; `users.remember_token` is one shared column. `DoctorDeviceSessionService::invalidate()` calls `Auth::guard('web')->logout()` at DoctorDeviceSessionService.php:203, so it must NOT be reused on the deny path — refusing login #2 would partially evict session #1, which requirement 1 forbids. Ruling P4, pinned by DoctorSingleSessionLeaseTest case 8.
- D9 — THE TWO-BROWSER PRIMITIVE IS SNAPSHOT / ACT / REPLACE / forgetUser. There is one session store in the test client, so acting as a second actor tears down the very session whose fate is being measured. The repo already learned this: crvRevokeViaRoute's docblock at tests/Feature/DoctorDeviceWebAuthn/DoctorPwaWebAuthnCredentialRevocationTest.php:196-217 records that the first draft proved containment by logging the doctor out itself, surfacing as the wrong denial reason and a dead Android session. `daInAnotherBrowser()` copies :218-231 including the mandatory `Auth::guard('web')->forgetUser()`.
- D10 — NEW SUITES GO IN `tests/Feature/DoctorAccess/` AND THE `DoctorAccess` TOKEN IS ADDED TO BOTH CRITICAL FILTERS AND THE MANDATORY REGISTRY. Verified finding H1: the two requirements are AND, not OR — `SelfHostedRunnerScanner::criticalGateSuiteCoveragePosture()` (app/Support/Cicd/SelfHostedRunnerScanner.php:470-518) appends an issue for EVERY variant whose filter fails to select a declared suite, and tests/Feature/Cicd/CriticalGateSuiteCoverageTest.php:49-60 asserts that posture is ok with exactly 2 filters. Verified the identity `Tests\Feature\DoctorAccess\...` is matched by no current token. Verified the append to `critical_gate_mandatory_suites` repins nothing: all seven readers use `->toContain`, never an exact-set `toBe`.
- D11 — MIGRATION COSTS E1 AND E8 ARE DISSOLVED BY OWNER DECISION O1, AND THE PLAN SAYS SO RATHER THAN INVENTING BREAKAGE. tests/Feature/AccessControl/DailyBranchContextLockTest.php:198-217 and tests/Feature/MasterData/DoctorRmeBranchSourceTest.php:272-311 all use UNSET doctors (no lock row), and O1 requires UNSET to preserve current behaviour EXACTLY. They stay green. What they need is an explicit premise assertion (`DoctorBranchLock` count is 0) so they cannot pass by accident under an implementation that locks unconditionally, plus a rename and a cross-reference to the LOCKED counterpart. Similarly E2 (LOCKED_ROLE_CONTEXTS at :219-227) stays green and becomes positive evidence the daily lock was left alone.
- D12 — WHAT THE CONCURRENCY TESTS PROVE, STATED WITHOUT OVERCLAIM. They prove: the loser of a race is refused once it acquires the lock; the row is genuinely locked while the winner is in flight (the NOWAIT 55P03 probe, with a mandatory prior sanity select proving the probe CAN see an unheld row); the database constraint holds independently of the service check; and the connection survives the unique violation on PostgreSQL. They do NOT prove wall-clock simultaneity, scheduler interleaving, or behaviour beyond two contenders — every case is sequential. They SKIP entirely on sqlite, so a green local run proves nothing about any of it. And the savepoint nesting depth differs: the concurrency suite runs at production depth 1/2, the RefreshDatabase suites at 2/3, which is why the aborted-transaction case lives in the concurrency suite.

## Risks
- R1 [CRITICAL] If the liveness probe reads the `sessions` table by the lease's recorded id, the feature is dead on arrival in BOTH environments for opposite reasons. In tests, SESSION_DRIVER=array (phpunit.xml:30) means the table is never written, so every incumbent reads DEAD and no denial is testable. In production, the id recorded at `Login` time is stale by one to three regenerations, so every incumbent ALSO reads DEAD and every second login is silently admitted. The tests that catch this are DoctorSingleSessionLeaseTest cases 3, 13 and 14; without case 3 the other two pass while enforcement does nothing.
- R2 [CRITICAL] The password step of a WebAuthn login mints a lease that the gate immediately abandons. `Auth::attempt` fires `Login` at app/Http/Requests/Auth/LoginRequest.php:45, the gate denies and calls `invalidate()` at app/Http/Controllers/Auth/AuthenticatedSessionController.php:83, and the WebAuthn completion then fires `Login` again at app/Modules/DoctorDevice/Services/DoctorDeviceWebAuthnLoginService.php:348. If invalidate() does not release, no doctor can ever complete a WebAuthn login, and tests/Feature/DoctorDeviceWebAuthn/DoctorPwaWebAuthnTest.php:528-543 fails with the error key changing from `credential` to `email`.
- R3 [HIGH] A denial on the recaller path would be an unhandled 500, not a login error. `Login` fires from `SessionGuard::user()` at vendor/laravel/framework/src/Illuminate/Auth/SessionGuard.php:202 during middleware guard resolution, where no controller is catching a ValidationException. DoctorSingleSessionLeaseTest case 10 pins that the refusal is a redirect, not a 500.
- R4 [HIGH] The partial unique index can be flattened by Laravel's schema grammar and no structural assertion can see it. `SchemaFacts::hasUniqueIndexOn()` (tests/Support/Database/SchemaFacts.php:88-102) reads name/unique/columns and never the predicate, and this exact flattening already happened once in this repo (database/migrations/2026_07_19_100010_reassert_single_primary_pilot_partial_unique_index.php:8-19). For a lease the consequence is not a weaker constraint but a permanently unreleasable one — a doctor could never log in a second time — and only in the local suite. The behavioural test (DoctorAccessGovernanceTest case 11: release, then re-claim) is the ONLY detector. Section K's probe found the raw-SQL form survives `ALTER TABLE ... ADD COLUMN` on sqlite 3.46.1, so the danger is the grammar, not the engine.
- R5 [HIGH] The new suites can be declared mandatory and still run in no gate. Declaring a path in `config/ci_runner.php` without a matching token in EVERY critical filter is a gate FAILURE, not an alternative satisfaction (finding H1, app/Support/Cicd/SelfHostedRunnerScanner.php:481-500). Both edits must land in the same commit as the files, because the scanner also fails on a declared path that does not exist.
- R6 [MEDIUM] `tests/Feature/MasterData/DoctorRmeBranchSourceTest.php` and `tests/Feature/Auth/SupervisorRmeRolePermissionTest.php` match no critical-gate token, so their repins will not be validated by any required PR gate. The Supervisor file is covered by the selective module gate's `Permission|AccessControl` filter (.github/workflows/foundation-evidence-gates.yml:900) only when the classifier routes the change as permission-touching; the MasterData file is covered by nothing but the weekly/dispatch full suite. Ruling P14 requires this be stated plainly rather than described as critical-gated.
- R7 [MEDIUM] The lease middleware runs AFTER `TouchOnlineContextLastSeen` (bootstrap/app.php:59-70), so the evicting request has already refreshed the doctor's presence row (app/Modules/RmeOnlineContext/Middleware/TouchOnlineContextLastSeen.php:19-28 → UserOnlineContextService.php:413). Without an explicit `markOffline()` in the eviction path the evicted doctor's clinic room stays occupied and blocks the next doctor via the check at UserOnlineContextService.php:522-532, for up to the inactivity window. Findings P5 and G15; DoctorSingleSessionLeaseTest case 16 asserts both halves.
- R8 [MEDIUM] A locked branch that loses `is_active` or `is_rme_enabled` turns `BranchContext::requireId()` (app/Modules/Branch/Services/BranchContext.php:54-63) into a RuntimeException on every write path — a 500 for a working clinician. Ruling P9 requires it degrade to UNSET-with-audited-warning; DoctorHomeBranchLockTest case 19 is the pin. This interacts with the fail-closed rule the daily lock uses (UserOnlineContextService.php:236-241), and the two must not be conflated: a doctor lock failing closed to null and then falling through to the online-context row would turn a deactivated branch into a route back into the session.
- R9 [MEDIUM] Hooking the lock into per-record authorization would be a patient-safety defect, and it is an easy accident. The patient-centric RM workspace anchors on the patient's EARLIEST visit, so a `ClinicVisitPolicy` hook would stop a doctor opening the Rekam Medis of a patient standing in front of them at their own locked branch whenever that patient's first RME visit happened elsewhere. Ruling P2; DoctorHomeBranchLockTest case 18 is the guard, and it must be written as an `assertOk()` on a real route, not as a unit assertion on a scope.
- R10 [MEDIUM] Adding `Doctor` to `DailyBranchContextService::LOCKED_ROLE_CONTEXTS` would satisfy the sprint superficially and break tests/Feature/AccessControl/DailyBranchContextLockTest.php:219-227, which is critical-gated via the `DailyBranchContext` token. It would also conflate a PER-DAY store (`trx_daily_branch_contexts`, UNIQUE(user_id, clinical_date)) with a PERMANENT lock — the wrong cardinality, as verified production fact J records.
- R11 [LOW] Adding `Doctor` to `RmeWorkingBranchScope::isContextBound()` (app/Modules/RmeOnlineContext/Services/RmeWorkingBranchScope.php:40-49) rather than consulting the lock directly in `branchIdsFor()` (:68-78) would route doctors through `activeContextBranchId()`, which fails closed to `[]` when the doctor is offline (:71-76). That BLANKS every doctor list rather than narrowing it. The DoctorHomeBranchLockTest list cases must include one where the locked doctor is OFFLINE and still sees their locked branch's list, or this failure mode ships undetected.
- R12 [LOW] Ticket burn on the Android deny path (ruling P16): the one-time login ticket is consumed before the lease claim, so a denial destroys it and the doctor must re-authenticate from scratch. The path is dead while enforcement is off, but DoctorSingleSessionLeaseTest case 6 must PIN whichever behaviour is chosen (pre-check availability before consumption, or accept the burn and document it) rather than leaving it unasserted.
