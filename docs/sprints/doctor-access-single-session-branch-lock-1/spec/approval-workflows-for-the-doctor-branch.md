# SLICE: Approval workflows for the doctor branch lock: (A) INITIAL ASSIGNMENT (UNSET → locked), (B) PERMANENT TRANSFER (locked A → locked B), (C) TEMPORARY BRANCH COVER (target branch + starts_at + ends_at + reason). Shape copied from the FEATURE-DAILY-BRANCH-CONTEXT-LOCK-1 exemplar (BranchChangeApprovalService/BranchChangeRequest/BranchChangeRequestRepository/routes/views) but with a permission-based authority (DoctorDeviceAuthorizationPolicy shape) instead of the exemplar's policy, whose `create()` predicate (app/Modules/RmeOnlineContext/Policies/BranchChangeRequestPolicy.php:54-60) requires a LIVE locked daily context — `DailyBranchContextService::LOCKED_ROLE_CONTEXTS` is exactly [ROLE_ADMIN_CLINIC, ROLE_KASIR] (app/Modules/RmeOnlineContext/Services/DailyBranchContextService.php:69-72), so it is false for every doctor and would 403 the whole feature.

## Decisions
- ONE permission, `approve_doctor_branch_lock`, covers initial assignment, permanent transfer AND temporary cover. Splitting cover into its own permission looks like least privilege and is actually a privilege escalation by duration: BRIEF section Q puts no upper bound on a cover, so a cover-only approver could chain covers and relocate a doctor permanently without ever touching the transfer workflow — the same outcome, through the weaker gate. The bound that makes the single permission honest is `config('doctor_branch_lock.cover.max_days')` (default 90), validated in the FormRequest and RE-ASSERTED inside the approval transaction so lowering the bound invalidates already-filed requests. Granted in RoleSeeder to Supervisor RME only, with no Super Admin entry — Super Admin arrives through the single global Gate::before (app/Providers/RepositoryServiceProvider.php:596-598), exactly as DoctorDeviceAuthorizationPolicy's docblock describes at app/Modules/DoctorDevice/Policies/DoctorDeviceAuthorizationPolicy.php:13-19.
- Authority is expressed as a PERMISSION and never as `hasRole('Supervisor RME')`. The exemplar's gate (`Gate::define('branch-change-request.approve', fn (User $user) => $user->hasRole('Super Admin'))`, app/Providers/RepositoryServiceProvider.php:593) is deliberately NOT copied: the product requires Supervisor RME as well as Super Admin, and the doctor-device inbox already solved exactly this with two permissions and no role comparison (routes/web.php:1684-1705, DoctorDeviceAuthorizationPolicy.php:29-46).
- The exemplar's POLICY is not reused. `BranchChangeRequestPolicy::create()` (app/Modules/RmeOnlineContext/Policies/BranchChangeRequestPolicy.php:54-60) requires a LIVE daily context whose `role_context` is in `DailyBranchContextService::LOCKED_ROLE_CONTEXTS`, which is exactly `[ROLE_ADMIN_CLINIC, ROLE_KASIR]` (app/Modules/RmeOnlineContext/Services/DailyBranchContextService.php:69-72) and is pinned false for doctors by tests/Feature/AccessControl/DailyBranchContextLockTest.php. Copying it would 403 every doctor. What IS copied is the TRANSACTION SHAPE and the message style, not the authorization.
- THE SELF-APPROVAL BOUNDARY HAS TWO COMPARISONS, NOT ONE, AND BOTH LIVE IN THE SERVICE INSIDE THE LOCK. The exemplar compares `requester_user_id === approver->id` (BranchChangeApprovalService.php:311-315) and explains at BranchChangeRequestPolicy.php:74-87 why the policy clause cannot be the boundary: `Gate::before` grants a Super Admin every ability BEFORE any policy method runs. This slice adds the comparison the exemplar has no need for — the SUBJECT is a doctor identified by `mst_doctors.user_id`, not by `requested_by_user_id`, so an approver who is themself the subject doctor passes the exemplar's check. The service refuses BOTH `request->requested_by_user_id === approver->id` and `doctor->user_id === approver->id`, after the doctor row is locked. The policy carries the same clauses as documented defence in depth for non-Super-Admins.
- THE APPROVE TRANSACTION IS: DB::transaction { lockById(request) → SoD comparisons → status re-assert → DoctorRepository::findForUpdate(doctor) (a real FOR UPDATE on mst_doctors, app/Modules/Doctor/Repositories/DoctorRepository.php:115) → refuse deactivated → refuse `user_id === null` → lockForDoctor(lock row) → STALE-SOURCE guard → destination re-validated for active+RME at decision time → cover/transfer guard → presence guard → write lock → markOffline → release lease → stamp decision → audit last }. Every step is the exemplar's (BranchChangeApprovalService.php:147-215) with the doctor lock and presence guard added. Note the codebase's nearest analogue, DoctorDeviceAuthorizationService::approve (app/Modules/DoctorDevice/Services/DoctorDeviceAuthorizationService.php:160-241), loads the doctor with an UNLOCKED `Doctor::query()->find()` at :178 — this slice deliberately does better, per ruling P10.
- THE UNLINKED DOCTOR IS REFUSED AT BOTH ENDS (ruling P6). A Doctor-role account with `mst_doctors.user_id = null` binds nobody: there is no session to invalidate, no presence to read and no room to free, so an approval against it would silently do nothing while reporting success. request() and approve() both refuse with 'Akun dokter belum terhubung ke data dokter. Hubungi admin untuk menghubungkan user ke master dokter.' — the wording already used by the FIX-PRE-68-45 doctor-performance hotfix, so operators see one message for one condition.
- A REVOKED-BY-STALENESS GUARD REPLACES THE EXEMPLAR'S DAY BOUNDARY. `BranchChangeRequest` carries `clinical_date` and refuses a previous-day row (`isStaleForClinicalDay`, app/Modules/RmeOnlineContext/Models/BranchChangeRequest.php:104-114, checked BEFORE the status at BranchChangeApprovalService.php:317-339 for the mutation-testing reason recorded there). A permanent lock has no day, so this slice has NO `EXPIRED` status and NO `expireStale()`. Its freshness boundary is the stale-source guard: the request type is RE-DERIVED from the live lock under the row lock, so an INITIAL_ASSIGNMENT whose doctor has since acquired a lock, and a TRANSFER whose lock has since moved, are both refused. Stating this in the status class prevents a later reader 'restoring' a state that was never missing.
- PERMANENT TRANSFER APPROVAL IS BLOCKED WHILE A COVER IS ACTIVE — EXACT RULE: inside the approval transaction, after `findForUpdate($doctor)` has serialized every decision for this doctor, `DoctorBranchCoverRepository::activeApprovedForDoctor($doctorId, now())` (status = approved AND starts_at <= now AND ends_at > now) must return null; otherwise refuse with 'Dokter sedang dalam periode cover sementara sampai {ends}. Selesaikan atau batalkan cover sebelum memindahkan cabang tetap.' A merely SCHEDULED (future-dated) cover does NOT block, because BRIEF section Q blocks only 'while an active cover exists' and a future cover creates no ambiguity about the CURRENT effective branch; the approver surface warns about it and the audit payload records its id. Initial assignment is unaffected — a cover cannot exist without a home lock, so an UNSET doctor can never have one.
- A COVER REQUIRES A HOME LOCK. Cover is defined in BRIEF section Q as temporary authority relative to a permanent home; with no home there is nothing to revert to, and expiry would silently WIDEN the doctor back to every RME branch — a widening on a timer, the exact inverse of a lock. request() and approve() both require `lockedBranchIdFor($doctorId) !== null`. This also removes an incoherent state the resolver would otherwise have to model.
- APPROVAL ALWAYS INVALIDATES THE SESSION, INCLUDING FOR A FUTURE-DATED COVER, AND IT DOES SO AS DATA. The service sets `released_at`/`released_reason` on the doctor's lease row inside the approval transaction and lets the sibling middleware tear the session down on the victim's next request — the shape IP6 argues for and the one `BranchChangeApprovalService::approve()` already relies on ('the operator's existing sessions resolve to the new branch on their very next request', :186-192). `DoctorDeviceSessionService::invalidate()` is NOT reused: its docblock at :181-187 explicitly refuses a global variant, and per BRIEF section R it calls `Auth::guard('web')->logout()` which cycles the SHARED `users.remember_token` (SessionGuard.php:650,:657). Releasing unconditionally — rather than only when the effective branch changes now — costs a future-cover subject one extra login and makes 'approval invalidates the session' true without a case analysis.
- THE ROOM IS FREED BEFORE THE SESSION IS TORN DOWN (ruling P5): `UserOnlineContextService::markOffline($subject)` runs first, which for ROLE_DOCTOR nulls `clinic_room_id` (app/Modules/RmeOnlineContext/Services/UserOnlineContextService.php:388-403). The exemplar's `realignOnlineContext()` (:373-380) is deliberately NOT copied: a doctor's context carries a room that belongs to the OLD branch, so realigning only the branch leaves an incoherent branch/room pair. The doctor re-selects both.
- PRESENCE IS SHOWN AND THE ONLINE CONFIRMATION IS ENFORCED SERVER-SIDE (ruling P11). The queue renders `UserOnlineContextService::isDoctorOnline($subject)` (:101-116) as a text badge; the approve form adds a required `acknowledge_online_impact` checkbox with the Indonesian warning about unsaved handwriting RM and odontogram input. The checkbox is UI. The BOUNDARY is the service re-reading presence inside the transaction and refusing when the doctor is online and the acknowledgement is absent — so a screen rendered ten minutes ago cannot approve past a doctor who has since come online.
- EXPIRY IS DERIVED, NEVER PERSISTED AND NEVER SCHEDULED. `ACTIVE` and `EXPIRED` are computed from `starts_at`/`ends_at` versus the evaluation instant by `DoctorBranchCoverStatus::derive()`; no column, no command, no queue job. The interval is HALF-OPEN [starts_at, ends_at) so two back-to-back covers are never simultaneously active and the overlap predicate is the clean `a.starts_at < b.ends_at AND b.starts_at < a.ends_at`. Every method takes the instant as an argument and none calls now(), which is what makes the whole time model testable under `Carbon::setTestNow()` with no bespoke freezing — the property ClinicalClock relies on (app/Support/Clinical/ClinicalClock.php:56-62).
- THE OVERLAP RULE HAS NO DATABASE BACKSTOP AND THE MIGRATION SAYS SO. A partial unique index cannot express a range predicate on either engine. The single serialization point is the `mst_doctors` row lock taken by `findForUpdate()` inside the approval transaction; the overlap query runs after it. Two partial unique indexes ARE created for what they can express — one PENDING request per doctor and one PENDING cover per doctor — created unguarded in the same migration as their tables, which BRIEF section K proves works on sqlite 3.46.1 and 2026_08_29_100002:24-29,:91-94 proves is the house pattern.
- EVERY INSERT THAT CAN HIT A PARTIAL UNIQUE INDEX USES THE NESTED-TRANSACTION (SAVEPOINT) SHAPE with the catch OUTSIDE it, and each service carries its own private `isUniqueViolation()` copy (23505 plus the three lowercase message probes) — verbatim from BranchChangeApprovalService.php:101-128 and :404-415, per BRIEF section N which records that the codebase duplicates this per service rather than sharing it. On PostgreSQL a failed statement aborts the whole transaction, so the naive catch-and-continue yields 25P02 on the exact race the code exists to handle — and passes on sqlite, which is why three pre-existing sites carry the broken shape undetected.
- A COVER MAY BE APPROVED BY ITS OWN REQUESTER; ONLY THE SUBJECT DOCTOR IS EXCLUDED. BRIEF section Q requires that a DOCTOR never self-creates or self-approves cover, and says nothing about maker-checker between administrators. Production has a thin approver tier, so a mandatory second administrator would deadlock cover on a single-Supervisor branch — the failure mode the legacy-migration sprint had to make configurable. Both `requested_by_user_id` and `decided_by_user_id` are recorded on every row, so a maker-checker rule can be added later as a config toggle without a schema change.
- THE APPROVAL SURFACES ARE FEATURE-GATED and 404 (not 403) when the capability is off, via the sibling `DoctorBranchLockResolver::enabled()`, which per ruling P7 must require BOTH `doctor.branch_lock` AND `doctor.single_active_session`. The predicate is NOT re-implemented in this slice's controllers — duplicating it is exactly the drift ruling P7 exists to prevent. Gating the approval workflow is the correct rollout order under owner decision O1: flag on, every doctor still UNSET and therefore on legacy behaviour, then assign one doctor at a time through the workflow. There is no backfill and no inference from doctor code, device branch, last login, room or history.
- `doctor_id` IS NEVER TRUSTED FROM THE REQUEST FOR A NON-APPROVER. The controller reads it only when the actor holds `approve_doctor_branch_lock`; otherwise it is discarded and replaced by `DoctorIdentityResolver::resolveForUser($actor)?->id` (app/Modules/Doctor/Services/DoctorIdentityResolver.php:35-40). The `exists` rules in the FormRequests are usability filters, not the boundary — the same framing StoreBranchChangeRequestRequest.php:19-23 states for its destination rule.
- AUDIT PAYLOADS CARRY IDS, BRANCHES, TYPE, STATUS, DECISION AND THE PRESENCE FLAG — no patient data, no doctor name, no KTP/NIK, matching the rule at BranchChangeApprovalService.php:382-388. Actions are `DOCTOR_BRANCH_LOCK_REQUESTED|APPROVED|REJECTED|CANCELLED`, `DOCTOR_BRANCH_COVER_REQUESTED|APPROVED|REJECTED|CANCELLED` and `DOCTOR_SESSION_LEASE_RELEASED_BY_APPROVER` — each under its OWN action, never reusing the device action `DOCTOR_SESSION_DEVICE_INVALIDATED` (ruling P8). All fit `sys_audit_logs.action` varchar(100) (database/migrations/2026_06_03_040005_create_sys_audit_logs_table.php:18); entity_type is the table name and fits varchar(150) at :16.
- THE APPROVER GETS A LEASE-RELEASE ACTION behind the same permission (ruling P17): POST `rme.doctor-branch-locks.release-session` with a mandatory reason, which frees the room and releases the lease in one transaction and audits it. It explicitly does NOT revoke a device, an authorization or a WebAuthn credential — WebAuthn revocation is irreversible and requirement 4 forbids it. It refuses when the subject has no linked user and when the approver is the subject.

## Risks
- THE SUBJECT-IS-APPROVER HOLE IS THE ONE A REVIEWER WILL MISS. The exemplar's self-approval check compares `requester_user_id` with the approver; here the person whose access changes is the DOCTOR, identified by `mst_doctors.user_id`, and they need never have filed the request. A Super Admin who is also a linked doctor sails through the policy (Gate::before returns true at app/Providers/RepositoryServiceProvider.php:596-598) and through the exemplar's comparison. Only the second comparison, inside the transaction after `findForUpdate($doctor)`, closes it. The test for it must construct exactly that actor or the pin is theatre.
- COVER EXPIRY HAS NO ENFORCER IN THIS SLICE. Approval releases the lease; expiry releases nothing, because doing so would require the scheduler that BRIEF section Q forbids as a security boundary. If the sibling middleware's effective-branch comparison is missing or subtly wrong, an expired cover keeps working for the length of the session. Mitigation available if that slice slips: refuse to approve any cover whose `starts_at` is in the future and cap `cover.max_days` low, so the exposure is bounded by session lifetime rather than by cover length.
- ONE PENDING REQUEST PER DOCTOR is enforced by the partial unique index, which means a Supervisor RME cannot file a transfer for a doctor who already has a pending SELF-filed assignment request — they must reject or cancel it first. This is intended (it is the exemplar's rule, 2026_08_29_100002:91-94) but it is a support call waiting to happen, and the refusal message must therefore name what is blocking and who filed it.
- BLOCKING TRANSFER APPROVAL DURING AN ACTIVE COVER can deadlock an operator whose cover runs for 90 days and who genuinely needs to move the doctor's home branch now. The escape hatch is `coverCancel`, which exists and is behind the same permission — but the refusal message MUST say so explicitly ('Selesaikan atau batalkan cover…') or the operator will read it as a wall. This is the only place the two workflows can jam each other.
- THE APPROVER QUEUE READS PRESENCE PER ROW. `UserOnlineContextService::isDoctorOnline()` (:101-116) performs several lookups per call including a branch and a room check, so a queue of N pending rows is N presence probes plus their sub-queries. Eager-load `doctor.user` in the repository (specified) and accept the cost at pilot scale (15 doctors), but do not let this pattern spread to a list that grows.
- `markOffline()` INSIDE THE APPROVAL TRANSACTION calls `upsertForUser` on `trx_user_online_contexts`, which has `unique('user_id')`. It is an update of an existing row in every realistic path, but if the row does not exist the method returns early (:390-393) and writes nothing — correct, and worth a comment so nobody 'fixes' it into a create that would bring an offline doctor online.
- EDITING `.github/workflows/foundation-evidence-gates.yml` puts the change into the CICD-CTRL-1 `ci_workflow` profile, the strongest one, forcing every gate to run. Correct for this sprint, but it also means the pre-existing red critical gate (62 Vite-manifest failures and 3 pint files, documented as pre-dating this branch and handed to CICD-FIX-1) will be visible on this PR and must not be mistaken for damage caused by this slice.
- THE HOME-LOCK PREREQUISITE FOR COVER is a rule this slice INVENTS from Q's definition rather than one Q states outright. It is defensible (expiry would otherwise widen an UNSET doctor back to every branch on a timer) but it is a product decision, and if the owner wants cover to work on UNSET doctors the guard is one condition to remove — plus a decision about what expiry then means.
- AN APPROVAL EVICTS A DOCTOR WHO MAY BE MID-CONSULTATION. The presence confirmation warns about unsaved handwriting RM and odontogram input, which is honest, but the system cannot save that input on their behalf. The only real mitigation is operational: the queue shows presence, the confirmation is mandatory, and the audit records `doctor_online_at_decision` so an incident can be reconstructed. Say this plainly in the runbook rather than implying the warning prevents the loss.
- THE THREE PRE-EXISTING BROKEN QueryException-INSIDE-TRANSACTION SITES (app/Modules/RME/Services/PatientDoctorAssignmentService.php:48 and :172, app/Modules/MedicalRecord/Services/DiagnosisRolloutService.php:127, per BRIEF section N) are NOT touched by this slice and must not be. They are reported to the owner as a separate finding; widening this sprint to fix them would put unrelated clinical-write code in a permissions PR.
