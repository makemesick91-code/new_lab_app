## FEATURE-DOCTOR-ACCOUNT-PERFORMANCE-INCOME-LINKAGE-1 — Doctor Account Identity Link (2026-08-31)

Branch `feature/doctor-account-performance-income-linkage-1` (base `feature/sprint-26-phase-26-8-stabilization-closure-go-watch-no-go-report`, baseline `revision-telkomas-branch-code-tkm1-to-tlk1-1-go` @ `8b3468e`; do NOT target main). Sprint doc `docs/sprints/feature-doctor-account-performance-income-linkage-1.md`; rule mirror `.cursor/rules/92-doctor-account-identity-link.mdc`. **Audit-then-build sprint. NO migration** — `mst_doctors.user_id` (nullable, **unique**, FK→`users`, `nullOnDelete`) has existed since Sprint 66.0 (`2026_06_29_120002`); no role/seeder grant, no income formula, no historical row touched.

**Audit verdict (CASE B — relation existed, UI did not).** Kinerja and Pendapatan are ONE feature: `rme.reports.doctor-performance` → sidebar "Kinerja & Pendapatan Dokter"; `DoctorPerformanceReportService::resolveAccess()` already resolved identity IDOR-safely from `mst_doctors.user_id`. But `user_id` was **unsettable through the application**: neither `StoreDoctorRequest` nor `UpdateDoctorRequest` validates it (so `validated()` strips it), `settings/doctors/_form.blade.php` has no account field, and unlike technicians (`lab:technician-link-user`) there was no CLI linker — while `rme:doctor-performance-access-audit` tells operators to *"Link the affected doctor accounts via master data"*, a control that did not exist. Only direct production SQL could link a doctor. **Second finding:** `DoctorUserResolver::resolveForUser()` fell back to case-insensitive **email matching**, and that resolver feeds `DoctorPatientScopeService` (which patients/visits/RM an account may open) and `UserOnlineContextService` visit doctor attribution — i.e. email was runtime clinical authority. Production at sprint time: 5 doctors / 2 linked / 3 unlinked, **0 users with the `Doctor` role**, 2 doctors whose email matched a user account (latent, unexploited, safely closable).

**Built.** (1) Canonical `App\Modules\Doctor\Services\DoctorIdentityResolver` — identity strictly from `mst_doctors.user_id`, **identity only** (`is_active`/branch/permission stay their callers' decisions, so no consumer policy changed). `DoctorUserResolver` now delegates to it with its `is_active` filter intact and **the email fallback removed** (unlinked accounts fail closed on the existing "belum terhubung ke data master dokter" message); `DoctorPerformanceReportService` resolves through the same service so kinerja/pendapatan can never drift onto a second notion of identity. (2) **Master Data RME → Relasi Akun Dokter**: routes `settings.doctors.account-links.{index,store,destroy}` declared **before** the `doctors` resource (static segment never shadowed — legacy-patient-import precedent), thin `DoctorAccountLinkController`, `LinkDoctorAccountRequest` (shape only), `DoctorAccountLinkService` (all eligibility + audited write), `DoctorPolicy::manageAccountLink`, view `settings/doctors/account-links/index.blade.php`, sidebar entry. (3) New permission **`manage_doctor_account_links`**, classified in `PermissionGroupingService` (`master_data` group — **mandatory**: three tests assert every `PermissionSeeder::PERMISSIONS` entry is grouped), granted to **no** role; Super Admin reaches it via `Gate::before`. Deliberately narrower than `manage doctors` so a future grant of doctor master-data maintenance to a clinic admin cannot silently also hand over the power to redirect who reads another doctor's income.

**Durable rules (mirror `.cursor/rules/92`):** auth identity ≠ clinical identity, joined only by `mst_doctors.user_id`; `DoctorIdentityResolver` is the single resolver (no ad-hoc `where('user_id')` in controllers/policies/views/tests); identity is NEVER inferred from name/email/phone; one account ↔ one doctor (locked service check **and** DB unique index); doctor self-access derives the doctor server-side and ignores a request `doctor_id`; an unlinked doctor account fails closed (never the first doctor, never a fake empty report); linking never rewrites visits/RM/invoices/payments/earnings; linking never grants a role; relink is explicit (`confirm_relink`), never a silent overwrite; every link/relink/unlink audits to `sys_audit_logs` (`DOCTOR_ACCOUNT_LINK`/`_RELINK`/`_UNLINK`) with technical ids only; **linkage chooses WHO the doctor is, it does not redefine HOW kinerja/pendapatan is calculated**; sidebar is UX only, route+policy authorization is the boundary.

**Usage:** Super Admin → Master Data RME → Relasi Akun Dokter → pick doctor → pick account (only active + `Doctor` role + unlinked are offered) → Hubungkan; tick **Ganti akun** to relink; **Putuskan** to unlink (doctor, account and all history preserved, self-access withdrawn immediately). Tests: `tests/Feature/MasterData/DoctorAccountLinkTest.php` (25). Deploy: **no migration**; run `db:seed --class=PermissionSeeder --force` + `permission:cache-reset`, then `rme:doctor-performance-access-audit`. Production doctors stay unlinked until an administrator links them deliberately.

**FEATURE-DOCTOR-ACCOUNT-PERFORMANCE-INCOME-LINKAGE-1 follow-up — CLI linker + a migration-order lesson (2026-09-01):** New `php artisan rme:doctor-link-user --doctor=<id|code> --user=<id|email> [--apply] [--confirm-relink] [--json]` (dry-run default) — thin wrapper over `DoctorAccountLinkService`, so the CLI enforces the identical guards and writes the identical `sys_audit_logs` row as the UI. It exists because on the pilot `tinker` is barred (psysh writes ERROR lines into the app log and pins the monitor to WATCH for 24h) and raw SQL would bypass both the eligibility checks and the audit trail. **Migration-order lesson:** removing the email fallback and adding the linking UI shipped together, which revoked doctor-workspace access for 2 live accounts (user 14→doctor 16, user 15→doctor 20) that had only ever resolved via email. Root cause was a measurement error — the pre-change count of Doctor-role users used an over-escaped `model_type = 'App\\Models\\User'` and returned 0 when the true count was 4. **Rule: when narrowing an identity resolver, measure who depends on the loose path first, and sanity-check that the measurement returns non-zero somewhere it should — a query matching nothing looks exactly like a clean estate.** Repair was owner-approved and persisted the mapping the system was already using; no historical row rewritten.

**§18/§19 print denial.** `rme.visits.print`, `rme.visits.pdf` (`ClinicVisitPolicy::print`) and `rme.odontograms.print` (`OdontogramPolicy::print`) are denied for a scoped Doctor. Both Blade actions were **already** wrapped in `@can('print', …)`, so the policy denial hides the buttons with no UI-only check — do not add one. **Prescription printing (`rme.prescriptions.print`) is out of scope and still works** (asserted alongside, which proves the denial is targeted, not blanket). Doctor read/edit lifecycle (consent gate, room gate, finalisation, historical immutability) is unchanged.

**§23 audit.** `DOCTOR_ROOM_ACCESS_REJECTED`, `DOCTOR_PRINT_RME_REJECTED`, `DOCTOR_PRINT_ODONTOGRAM_REJECTED` via the shared `AuditLogService`/`sys_audit_logs`. Payload is identifiers + status only; no PII/KTP/NIK.

**`completeExamination` is deliberately NOT room-guarded** — the HTTP path authorises `transition` (room-guarded) first and the ability is re-checked inside `ClinicVisitService::transitionStatus()`; guarding it too would strand a doctor whose online context lapsed mid-encounter (CI caught this via 8 `tests/Feature/Pilot/RmeLabCandidateE2EValidationTest` failures). `MedicalRecordPolicy` deliberately untouched: `MedicalRecordController@show` authorises `view` on the **opened** visit before the Sprint 64.0 canonical redirect, so the RME surface is covered without disturbing the patient-centric workspace resolver.

**Test-fixture contract changed (2 files, superseded assertions).** `RoomAssignmentWorklistTest` now pins the doctor's online room (`$this->doctorRoom`) and puts the doctor-facing visits in it — a doctor is only ever scoped to the room they are working. `DoctorPatientScopeTest::scopeVisit()` defaults `clinic_room_id` to `test()->room` (the room `scopeDoctorOnline` uses) instead of inventing a throwaway room per visit, otherwise patient-scope tests silently become room-scope tests. Two Sprint 66.2 assertions that a Doctor may **print** another doctor's odontogram now assert `assertForbidden()` (§19), and the shared-patient test asserts sharing survives via **history** while the other room's live encounter stays forbidden (§16/§17).

**Known finding left untouched (§22):** `GET rme/online-context/rooms` may disclose room metadata cross-branch for an arbitrary `branch_id`. Mapped and NOT on this sprint's critical path — Phase 1 never reads a room from the request. Recorded, not half-fixed, not bundled.

The repository's `create()` uses `forceFill` on purpose — `$fillable` guards against REQUEST mass assignment, while the service payload is the real allow-list (it must write `uuid`/registration stamps).

**Branch binding** is server-authoritative: an active RME-enabled branch (`BranchService::rmeEnabledIds()`), re-validated on create AND update. Canonical codes only (`TLK1`, `SPN4`).

**Authorization:** new `view_doctor_devices` + `manage_doctor_devices` seeded but granted to **NO role** → Super Admin only via the global `Gate::before` (the ENT-7 `view_developer_console` precedent). M2 is therefore a **compound** mutant (both barriers removed) and is killed in that form.

**Gotcha:** module controllers must `use AuthorizesRequests` — Laravel 12's base `Controller` has no `authorize()`, so `$this->authorize(...)` fatals with a 500 without the trait.

**CI:** both suites registered in `ci_runner.critical_gate_mandatory_suites` + a `DoctorDevice` token added to BOTH critical variants (they must stay identical) — the Phase 1 lesson that a suite no token selects is a control nothing enforces.

Sprint doc `docs/sprints/feature-doctor-trusted-android-device-lock-1-phase-3-5.md`; decision `docs/adr/0009-android-production-signing-distribution-and-device-management.md`; governance `docs/governance/android-production-signing-governance.md`; runbooks `docs/runbooks/android-{release-distribution-and-rollback,signing-key-backup-and-recovery,device-loss-replacement-and-decommission,clinic-device-provisioning}.md`; procurement `docs/operations/clinic-tablet-procurement-specification.md`; rule mirror `.cursor/rules/141-android-production-release-governance.mdc`.

**READINESS AND GOVERNANCE ONLY.** `DEVICE_ENFORCEMENT_ACTIVE=false`, `DOCTOR_BROWSER_LOGIN_DENIED=false`, `ANDROID_REAL_DEVICE_VALIDATION=false`, **`PRODUCTION_SIGNING_KEY_PROVISIONED=false`**. Full feature stays **NO-GO**; `feature-doctor-trusted-android-device-lock-1-go` is **still NOT created**. **No migration, no route, no permission, no frontend, no schema.** Phase 1 room scope + RME/odontogram print denial, Phase 2 registry lifecycle, and Phase 3 enrolment/replay/WebView contracts all unchanged.

**What changed is the Phase 3 posture line "production signing governance is UNRESOLVED" — now RESOLVED (ADR 0009).** Rule 11 of `140-android-clinic-device-identity.mdc` is superseded by rule 141; 140's other rules stand.

**The four decisions.** (1) **Signing = Play App Signing**: Google KMS holds the app signing key, the clinic holds only an **upload** key. The deciding property is narrow — an upload key is *resettable*, an app signing key is not — and in this system losing the app signing key destroys **every device enrolment**, because clearing app data destroys the Keystore identity and the forced reinstall generates a key no administrator approved. Rejected: self-managed keystore (every failure terminal), keystore in CI secrets (PR CI runs untrusted code ⇒ every fork a release authority), MDM-only signing (vendor without removing the problem). (2) **Distribution = Managed Google Play private app** (AAB; package name **permanent from first publish**). (3) **Device management** = self-owned Device Owner (pilot) → EMM dedicated device (fleet, ≥5); under EMM **our app is NOT the Device Owner**, the DPC is. (4) **Rollback = halt rollout, then forward-fix under a HIGHER versionCode** — Play refuses a non-greater versionCode and Android blocks downgrade installs, so "reinstall the previous APK" does not exist; halting does not recall already-updated devices; the **first release on a track cannot be halted at all**.

**Pilot exception, bounded not discovered:** a self-owned Device Owner tablet has **no Google account** (a precondition of `dpm set-device-owner`), so it cannot install from Managed Google Play. The single pilot device side-loads the **Play-signed** artifact over ADB — identical signing identity, different transport. Side-loading a *locally* signed build is forbidden: it validates an identity production never uses.

**Deliberately NOT done: no production key was created.** Creating an irreplaceable signing identity on an ephemeral context with no recorded custodian, to make a sprint look green, is the exact failure this governance exists to prevent. The procedure was instead rehearsed end to end with a **disposable** key (generated → signed v1 → encrypted backup → primary shredded → restored → signed v2), and the decisive evidence is that **v1 and v2 carry an identical signer certificate** — which is what an Android update actually requires. Comparing the PKCS#7 blocks instead reports a false failure (they are signatures over each artifact's own content). Honest pair: `SIGNING_RECOVERY_RUNBOOK_TESTED_WITH_DISPOSABLE_KEY=true` / `PRODUCTION_KEY_RECOVERY_VERIFIED=false`.

**Built:** `config/android_release.php` (all forbidden literals live here, never in the scanner); `app/Support/Android/KotlinSourceScanner.php` (comment stripping, literal-**aware**, nesting block comments); `app/Support/Android/AndroidReleaseGovernanceScanner.php` (17 read-only checks; signs nothing, needs no secret, no network — safe on a fork PR); `php artisan android:release-readiness [--json] [--strict] [--manifest=]`. Suite `tests/Feature/DoctorDevice/DoctorDeviceAndroidReleaseGovernanceTest.php` (31) registered in `ci_runner.critical_gate_mandatory_suites`.

**Gotcha — do not over-apply the Phase 3 comment-stripping lesson.** Rule 13 of 140 says strip comments so a guard stops matching its own prose. Applying that as "blank the strings too" **breaks this guard**: the forbidden token is `signingConfigs.getByName("debug")`, which *contains a string literal*, so blanking strings makes it unmatchable and a genuinely debug-signed release passes. Literal awareness means "a `//` inside a string does not open a comment", never "delete the string". Mutant M8 pins exactly this.

**Mutation finding — M2 survived the first cut.** Emptying the key-material pattern lists left both `no_committed_key_material` and `keystore_ignored` reporting PASS while enforcing nothing: an absence assertion over an empty list passes on nothing at all. Fixed by a `key_material_guard_armed` check that fails closed on an empty or disarmed list. ## DOCTOR-PWA-WEBAUTHN-1 — WebAuthn device credentials for the doctor browser login (2026-09-08)

Branch `feature/doctor-pwa-webauthn-1` (base `feature/sprint-26-phase-26-8-stabilization-closure-go-watch-no-go-report` @ `352017b1`, which carries `pwa-foundation-1-go` @ `e4fa78b1` — the commit production runs; do NOT target main). Durable contract `docs/architecture/doctor-pwa-webauthn.md`; rule mirror `.cursor/rules/93-doctor-pwa-webauthn.mdc`; manifest `.sprint/current.yml`. **Deployed with the capability flag OFF. NOT GO** — a GO tag additionally requires a ceremony on the real pilot tablet, which no automated test can substitute for.

**What it adds:** a browser on an **approved clinic device** can earn *the same* server-verified device binding the Android Clinic App earns, by producing a WebAuthn assertion instead of a keystore signature. `DoctorAppLoginGate` denied a browser for one reason — only ticket redemption ever wrote `doctor_device.device_id` — so this adds a **second writer of that one binding**, not a second enforcement authority. Consequence: revocation, branch scope and the per-request middleware already work for browser sessions on day one, through machinery written and tested for the Android path.

**Reuse, not duplication.** `mst_doctor_devices` IS the clinic device; `mst_doctor_device_authorizations` already modelled many doctors per tablet. Only the credential store is new. **The WebAuthn "user" is the DEVICE** (userHandle = device uuid) — binding it to a doctor would make a shared tablet impossible to model.

**Migrations (additive only):** `trx_doctor_device_webauthn_credentials`, `trx_doctor_device_webauthn_challenges`. **Library:** `web-auth/webauthn-lib` ^5.3 (no hand-rolled CBOR/COSE/signature code); `composer.json` gains `config.platform.php = 8.3.6` so the lock resolves for production's **php8.3-fpm** (local PHP is 8.5 — the known lock-mismatch trap). Delta: 9 added, 0 removed, 7 patch bumps.

**The security decision that matters:** `authenticatorAttachment: "platform"` does **NOT** mean device-bound — a modern Android platform authenticator routinely creates a *synced passkey* that is also on the doctor's personal phone. Only the **BE (Backup Eligible)** flag distinguishes them, so `WEBAUTHN_REQUIRE_DEVICE_BOUND` (default true) refuses `BE=1` at registration. `BS` is deliberately not the gate (mutable; reports 0 until it syncs), and `unknown` is refused too — silence is not a pass.

**Two independent switches.** `doctor.trusted_device_enforcement` (unchanged) must be on for a browser to be denied at all; only then is `doctor.pwa_webauthn_device_login` (new, default false, risk critical) reachable. The new flag **admits, never denies**, and can only admit an account already holding a credential on an ACTIVE device with an ACTIVE authorization — production holds zero. Turning it off ends open **WebAuthn** browser sessions on their next request — see DOCTOR-PWA-WEBAUTHN-PROOF-BINDING-1 below, which is what made that true on a device that also holds an Android keystore key.

**Gotchas worth not relearning:**
- `Cose\Algorithm\Manager::create()` takes **no arguments**; PHP silently ignores an array passed to it, yielding an EMPTY manager that fails much later as `Unsupported algorithm` on the first real assertion. Use `create()->add(ES256::create(), RS256::create())`.
- Never bind a ceremony to `session()->getId()` — it rotates legitimately (`regenerate()` at login, twice on this path) and the failure mode is a doctor locked out. Bind to a random token in **session data**, which survives `regenerate()` and dies with `invalidate()`/`flush()`.
- `DoctorAppLoginGate::deviceUsable()` demanded the **Android keystore key** as the only identity proof, and the per-request middleware calls it — so a browser-bound session would have been torn down on the very next request. This sprint made it accept either proof, flag-gated. That widened nothing for Android (a WebAuthn-only device has no `public_key`/fingerprint, so `DoctorAppLoginService` cannot find or verify it) but it did open the **reverse** substitution on a dual-proof device — closed by DOCTOR-PWA-WEBAUTHN-PROOF-BINDING-1 below, which deleted `deviceUsable()`.
- `authentication_coupled_only_through_the_gate` (AndroidReleaseGovernanceScanner) forbids a "proof service" in `app/Http/Controllers/Auth`. The WebAuthn branch therefore goes through `DoctorAppLoginGate::deviceCredentialLoginAvailable()` and `DoctorDeviceSessionService::beginDeviceCredentialLogin()` — both already sanctioned. **Refactor to keep the invariant true; do not widen the allow-list.**
- Route names in the doctor-device group carry a `settings.` prefix (`settings.doctor-devices.webauthn.*`).
- A JS comment containing a banned literal trips the regression that scans the file for it — the same trap as the UI governance scanner.

**Not changed:** the Android `/device-api/v1/*` endpoints, enrolment protocol, tickets, the APK (**not retired**), the service worker (WebAuthn paths are uncached because the worker is deny-by-default — no denylist added), clinical data still online-only, no new permission (enrolment reuses `manage_doctor_devices`, which is the same human who approves devices).

**Pre-activation check:** `php artisan webauthn:readiness` (`--json`; add `--report-only` to look without gating, `--strict` to also fail on an unusable relying party). **D7: the bare command now FAILS CLOSED unless every active device has a fresh server-verified assertion** — liveness was previously opt-in behind `--require-live-proof`, which no call site anywhere ever passed. — read-only, safe on production, reports the resolved RP id/origins, whether a ceremony is possible, both switches, and COUNTS (never a credential id, public key, device name or doctor name). An RP misconfiguration fails silently *inside the browser*, so it must be checkable from the server first. `--strict` fails only on an unusable relying party; "no credentials yet" is a state, not a fault.

**Tests:** `tests/Feature/DoctorDeviceWebAuthn/DoctorPwaWebAuthnTest.php` (39) driven by `tests/Support/FakeWebAuthnAuthenticator.php` — a **real** software authenticator (genuine EC P-256 key, real authenticator/client data, OpenSSL signatures) so forged signatures, replayed challenges, foreign origins, revoked credentials/devices/authorizations and cross-browser payload reuse are all genuinely exercised; plus `tests/js/doctor-device-webauthn.test.mjs` (3). Green: DoctorDevice+Auth+AccessControl+DoctorDeviceWebAuthn **667 passed**, `Pwa|FeatureFlag|Phase4a` 160 passed, `npm run test:js` 40 passed.

**Relationship to the frozen Phase 4A pilot (not a conflict):** production is ARMED for drg Karmila (user 18, Cabang Sunu) with PR #392 open and unmerged. That enforcement denies her **browser** precisely because a browser had no way to write a device binding. This sprint supplies that way — cryptographically, only on an approved device — so it does not weaken the armed pilot; it is the mechanism by which the same armed enforcement can admit a verified browser. It admits nobody on deploy.

## DOCTOR-PWA-WEBAUTHN-PROOF-BINDING-1 — a session remembers the proof that authenticated it (2026-09-08)

Branch `feature/doctor-pwa-webauthn-proof-binding-1`, base `feature/sprint-26-phase-26-8-stabilization-closure-go-watch-no-go-report` @ `f0da6f90` (the DOCTOR-PWA-WEBAUTHN-1 merge — exactly what production runs). Contract: `docs/architecture/doctor-pwa-webauthn.md` §12; rules `.cursor/rules/93-doctor-pwa-webauthn.mdc` 27–39. **No migration, no route, no permission, no new flag, no default changed.**

**The defect, and why the parent sprint's own tests could not see it.** `deviceIdentityProven()` answered *"does this device hold **some** acceptable proof?"* and the per-request middleware used it to answer *"is the proof that established **this** session still valid?"*. Those coincide on a single-proof device — and every fixture in `DoctorPwaWebAuthnTest` is a `DoctorDevice::factory()` device (`identity_state = unverified`, `public_key = null`). **The pilot tablet is not.** `PHASE4A_PILOT_TABLET_02` (device 3, authorization 2) is ACTIVE, `cryptographically_verified`, with an Android keystore key, so the Android branch returned `true` *before* the WebAuthn flag or the credential was ever read. Consequence, measured not theorised: on that device a WebAuthn browser session **survived the kill switch** and **survived revocation of the very credential that authenticated it**. New logins were always fine — `completeLogin()` verifies a real assertion. The hole was **existing-session containment**.

**The fix.** New immutable `App\Modules\DoctorDevice\Support\DoctorSessionProof` (`android_keystore` | `webauthn` + credential row id). `DoctorDeviceSessionService::bind()` now takes the proof as a **required** argument and writes `doctor_device.proof_type` + `doctor_device.webauthn_credential_id`; the Android redemption path passes `androidKeystore()`, `completeLogin()` passes `webAuthn($credential->id)`. **The proof is recorded by the path that ran and never inferred afterwards from what the device carries** — that inference *is* the bug. `deviceUsable()` and `deviceIdentityProven()` are **deleted**, not documented-around, and replaced by `deviceProofDenyReason()` / `deviceUsableForProof()`, which login-time and per-request now share so the two can never disagree.

**Resulting contract (all four rows hold on a DUAL-PROOF device, the only place the first two were ever in doubt):** WebAuthn session + flag OFF → **deny next protected request**; WebAuthn session + credential revoked → **deny**; Android session + WebAuthn flag OFF → **unchanged**; Android session + WebAuthn credential revoked → **unchanged**. Device revoke and authorization revoke stay terminal for both. The WebAuthn credential is re-checked *scoped to the bound device*, so "revoked", "names nothing" and "belongs to another tablet" all deny; the device-binding verdict is re-checked per request too, so a **tightened** policy ends sessions admitted under the looser one.

**Missing `proof_type` is DENIED (Strategy A), deliberately.** Reading an absent proof as Android — even "only when the device really has a keystore key" — is the same substitution one level up, and would grandfather exactly the sessions this sprint contains. Blast radius is bounded: only a doctor **inside the armed enforcement scope** holding an open bound session at deploy time, i.e. one account, whose tablet re-login is the path it already uses. Same denial covers an unrecognised `proof_type` and a `webauthn` binding with no credential reference.

**Audit reuses what exists.** Three stable codes — `session_proof_unknown`, `webauthn_login_disabled`, `webauthn_credential_not_usable` — ride the existing `DOCTOR_SESSION_DEVICE_INVALIDATED` entry `DoctorDeviceSessionService::invalidate()` already writes. No new audit subsystem, no per-request success logging. All three render **one** message: naming the withdrawn proof maps the device estate and helps nobody sign in.

**Gotchas worth not relearning:**
- **A containment test on a single-proof fixture proves nothing about a dual-proof device.** The two parent tests that looked like exactly this coverage passed for a reason that does not hold in production. New suite `tests/Feature/DoctorDeviceWebAuthn/DoctorPwaWebAuthnProofBindingTest.php` builds the real production shape (real EC P-256 software authenticator **and** a real Android keystore signature over a server nonce, one device, both), and its two headline cases **fail on the pre-sprint code** with `Failed asserting that true is false`.
- `authentication_coupled_only_through_the_gate` scans for identifiers containing `DoctorDevice` in `app/Http/Controllers/Auth`, `app/Http/Middleware`, `app/Services/Auth`, `app/Modules/ClinicVisit/Middleware`, `bootstrap/app.php` and the watched `app/Modules/DoctorDevice/{Middleware,Listeners}`. `DoctorSessionProof` does not contain the token and is never referenced from a scanned surface — **the allow-list was not widened**.
- The `|DoctorPwaWebAuthn` CI filter token already selects the new class, but it is also registered in `config/ci_runner.php` `critical_gate_mandatory_suites` so coverage reconciliation fails loudly if the token is ever dropped.

**Not changed:** enrolment, the ceremony, challenge protocol, relying party, device registry, authorization model, branch scope, the service worker, the Android `/device-api/v1/*` endpoints, the APK, both flags' defaults, and the Phase 4A enforcement scope. Device 3 and authorization 2 are **not** mutated; no credential is registered; nothing is armed.

**This GO tag is not the parent's.** `doctor-pwa-webauthn-proof-binding-1-go` means the proof-binding hardening is production-ready. `doctor-pwa-webauthn-1-go` **remains forbidden** until a ceremony runs on the real Samsung tablet — BE/BS are a hardware measurement and no simulated authenticator can stand in for them.
