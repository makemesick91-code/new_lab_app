## FEATURE-DAILY-BRANCH-CONTEXT-LOCK-1 — Daily Working-Branch Lock for Kasir & Admin Klinik (2026-08-29)

Branch `feature/daily-branch-context-lock-1` (base `feature/sprint-26-phase-26-8-stabilization-closure-go-watch-no-go-report`, BASE_SHA `b9d05a8`; production runtime at start `76bd7c0` / tag `feature-legacy-import-hub-1a-rme-activation-go` — the base tip was one docs-only commit ahead, deliberately undeployed). Sprint doc `docs/sprints/feature-daily-branch-context-lock-1.md`; rule mirror `.cursor/rules/92-daily-branch-context-lock.mdc`; manifest `.sprint/current.yml`.

**The defect closed.** A **Kasir** or **Admin Klinik** could change working branch as often as they liked by simply re-opening the online-context selector (`POST /rme/online-context/kasir|admin-clinic`), which rewrote the single `trx_user_online_contexts` row. That row is priority #1 in `BranchContext::forUser()` and `RmeWorkingBranchScope` resolves the whole clinic-operations **and cashier financial** workspace from it, so a free re-selection silently moved which invoices, receivables and payments the cashier could act on. Proven on the baseline with a probe (select A → `BranchContext`=A; select B → `BranchContext`=B, both passing); that probe is now inverted in the shipped suite.

**Contract.** First branch of a clinical day = free; a second *different* branch = refused until a Super Admin approves; the *same* branch again = idempotent; a new clinical day = one new free selection. **Doctor and Perawat are deliberately NOT locked.**

**The authority is a table, never the session.** New `trx_daily_branch_contexts`, `UNIQUE(user_id, clinical_date)`, `current_branch_id` = the authority. `UserOnlineContextService::activeContextBranchId()` lets it **override** the session-scoped online-context row, so a tampered/stale `branch_id` does not move the scope and an approved switch takes effect in every existing session on the next request. The override only ever *replaces* a branch, never resurrects a `null` (an offline operator still has no working context).

**Key key.** Uniqueness is `(user_id, clinical_date)` and deliberately **NOT** `role_context` — a user holding both `Kasir` and `Admin Klinik` would otherwise open one role context at one branch and the other at a second branch on the same day. One human, one clinical day, one branch.

**Guard placement.** `DailyBranchContextService::assertSelectable()` is called inside `startAdminClinicSession()`/`startKasirSession()` **after** the branch-eligibility assert — the single chokepoint covering HTTP, console and the test helpers at once, and ordered so an approved switch can never become a route to a branch the user was not entitled to work in.

**An approval is an event, not a credential.** The switch is applied INSIDE the approval transaction, so there is no replayable token. Every binding is re-asserted under the row lock: user (the requester's context is locked, not the approver's), **source** (the live context must still sit on `source_branch_id`, else stale → refused), **destination** (re-validated for eligibility at decision time — an approval is never a grant of access to a branch the user could not otherwise work in), **clinical day** (a previous-day request is refused **without relying on a cron**).

**Two gotchas found by testing, not review, both in the day-boundary guard.** (a) An opportunistic `EXPIRED` stamp inside the decision transaction is rolled back by the very exception that refuses the decision. (b) Moving that stamp to a pre-transaction step then made the staleness guard **unreachable** — the refusal a test observed actually came from the `isPending()` check a few lines later, so deleting the guard left every test green (caught by mutation M13). Final design: staleness is checked FIRST, inside the locked decision, and is the single observable boundary; the `EXPIRED` bookkeeping lives only in the queue listing (`BranchChangeRequestRepository::expireStale`, called by `index()`). The test asserts the row is still `PENDING` at the moment of the attempt, so the refusal can only be the guard.

**Self-approval is NOT enforced by the policy.** `Gate::before` grants Super Admin every ability before any policy runs, so `BranchChangeRequestPolicy::decide()`'s self-check never executes for the one actor who could be both. The enforced comparison lives in `BranchChangeApprovalService::lockPendingRequest()`. The policy clause is defence-in-depth for non-Super-Admins.

**No new permission.** Approval authority is the canonical Super Admin role, published once as the `branch-change-request.approve` gate and consumed by BOTH the route group and the sidebar (same shape as `satusehat.access`). Inventing `approve_branch_switch` would let approval authority be granted to someone the lock constrains.

**Mass assignment gotcha.** `status`/`decided_by_user_id`/`decided_at`/`decision_note`/`applied_at` are absent from `BranchChangeRequest::$fillable` (a forged `status=approved` has nowhere to land) — which means `update()` **silently discards** exactly the fields a decision must write. The repository therefore uses `forceFill`, and `create()` states the initial `pending` status explicitly (a mass-assigned create returns a model with NO `status` attribute, so `isPending()` answers false on a genuinely pending row).

**Migrations (additive only — `migrate`, never `migrate:fresh`/`db:wipe`):** `2026_08_29_100001_create_trx_daily_branch_contexts_table`, `2026_08_29_100002_create_trx_branch_change_requests_table` (partial unique index `WHERE status='pending'` = at most one open request per user per clinical day; branch FKs `restrictOnDelete`). **No seeder, no permission, no role change.** **First-day note:** on deployment day every locked operator's next selection is their free first selection, because no daily context exists yet — intended, not a gap.

**Clinical day** comes from `ClinicalClock` (Asia/Makassar), never `Carbon::today()`. The interval is a **calendar day**, not a rolling 24 hours from the first selection; both properties are pinned with a frozen clock (23:59:59 WITA still locked, 00:00:00 WITA free again, and a 09:00 selection does not stay locked until 09:00 tomorrow).

**PostgreSQL transaction-abort trap (found by CI, invisible to SQLite).** PostgreSQL aborts the WHOLE transaction on any failed statement (`25P02` thereafter until rollback), so catching a unique violation and continuing — green on SQLite — leaves a poisoned connection. Hit BOTH violation handlers; the serious one was `assertSelectable()`'s first-selection race re-read, which runs inside `DB::transaction` and was therefore **broken on production PostgreSQL**. The PG concurrency suite missed it because its cases are refused by the lock check before reaching the INSERT. Fix: wrap each INSERT in a nested `DB::transaction` (Laravel = `SAVEPOINT`). Verified by reproducing on `postgres:16.14` then re-running: `tests/Feature/AccessControl` = **108 passed on PostgreSQL where nothing skips** (SQLite reports 9 skipped). **Standing rule: code that catches a DB error and continues must be exercised against PostgreSQL, never trusted from a SQLite run.**

**Concurrency** is database-level: `UNIQUE(user_id, clinical_date)` (the first-selection loser re-reads the committed winner and is judged against it — never a second context), the partial unique index, and `lockForUpdate()` on both the context and the request row. Row locks are unobservable on SQLite, so `DailyBranchContextConcurrencyTest` runs on **PostgreSQL 16** and **skips out loud** elsewhere (pattern lifted from `LegacyImportHubConcurrencyTest`).

**Surfaces.** `rme.branch-change-requests.{create,store,cancel}` for the operator; `.{index,approve,reject}` behind the Super Admin gate. All six are added to `EnsureRmeOnlineContext::EXEMPT_ROUTE_NAMES` — without it a locked-but-offline cashier is bounced to the selector where the only branch offered is the one they are escaping. It widens nothing: `BranchChangeRequestPolicy::create` still requires a daily context that only a completed selection creates. The online-context selector now renders the locked branch (single option + "Ajukan Pindah Cabang") instead of a free dropdown that only fails on submit; the hidden option is a courtesy, the server guard is the boundary.

**Blast radius:** exactly one existing test changed — `FixClinicOpsWorkingBranchContextTest > "follows the cashier to a new branch when the working context changes"`. Its intent (cashier scope follows the working branch) is unchanged and still asserted; it became two tests — refused without an approval, applied with one.

Tests: `tests/Feature/AccessControl/{DailyBranchContextLockTest,BranchChangeApprovalTest,DailyBranchContextBypassTest,DailyBranchContextConcurrencyTest}.php` + `tests/Feature/AccessControl/helpers.php`. CI: `DailyBranchContext|BranchChange` added to BOTH critical-gate filter variants and the four suites declared in `config/ci_runner.php` `critical_gate_mandatory_suites` (a security control that the gate never selects is not a control).

## REVISION-TELKOMAS-BRANCH-CODE-TKM1-TO-TLK1-1 — Telkomas Branch Code Foundation (2026-08-31)

Branch `revision/telkomas-branch-code-tkm1-to-tlk1-1` (base `feature/sprint-26-phase-26-8-stabilization-closure-go-watch-no-go-report`, baseline `2fb8c4c` / tree `80e5404b` / GO tag `bugfix-legacy-odontogram-queue-consumer-1-go`, confirmed as live production HEAD before work began; do NOT target main). Doc `docs/sprints/revision-telkomas-branch-code-tkm1-to-tlk1-1.md`; rule mirror `.cursor/rules/92-telkomas-branch-code-canonical.mdc` (SUPERSEDES the "TKM1 = Cabang Telkomas" registry line in rule 73 and in the RME-BRANCH-SUN4 block above).

**TELKOMAS BRANCH CODE FOUNDATION.** Cabang Telkomas canonical branch code is **`TLK1`**. `TKM1` is deprecated and must never be generated for new application records, new patient medical-record numbers, active branch mappings, new imports, reports, exports, fixtures, or other canonical application output. `TKM1` is accepted ONLY as a historical compatibility alias where pre-existing identifiers or immutable historical evidence require it. `TKM1` and `TLK1` resolve to the SAME Telkomas branch identity (same `mst_branches` row, same id, same patients), but the canonical code the application emits is `TLK1`. Historical RM values using `TKM1` resolve to their canonical `TLK1` form. Production RM migration is collision-safe, transactional, auditable and fails closed; it never creates duplicate patients and never changes the Telkomas branch primary identity. Immutable published clinical evidence and historical audit records are NOT rewritten merely to replace `TKM1` text. Unknown, ambiguous, inactive or invalid branch codes **fail closed** — there is no `unknown → Telkomas` fallback and no fuzzy matching.

**What the inventory found (this was not a cosmetic rename).** Production `mst_branches` id 1 had ALREADY been renamed to `TLK1` by hand while the repository still said `TKM1`, producing three defects — one live, two latent: (1) `RmeBranchSeeder` looked Telkomas up by `TKM1` alone, so the next routine `db:seed --class=RmeBranchSeeder --force` would have **created a duplicate "Cabang Telkomas"**, splitting one clinic's patients across two branch ids (branch id is the isolation boundary); (2) legacy-archive branch derivation resolved `Branch::where('code', 'TKM1')` → not found, so patient 36 (`DG-TKM1-2024-9985`) had an **unreachable** legacy RME/odontogram archive; (3) the WAVE-4 allowlist admitted the literal token `TKM1` from the environment while derivation reported `TLK1`, which would have **locked Telkomas out of the wave it is approved for**.

**Design.** One-way alias policy in `App\Modules\Branch\Support\BranchCodeAlias` (`canonicalize`/`isHistoricalAlias`/`historicalAliasesFor`/`equivalentCodes`); **never** `$code === 'TKM1' || $code === 'TLK1'` at a call site. `PatientMedicalRecordNumberService::branchCodeFrom()` now reports the CANONICAL code (so `LegacyRmeBranchResolver` and `LegacyOdontogramBranchBindingService` needed **no change** — one fix serves both), plus new `literalBranchCodeFrom()` (the historical fact), `canonicalizeBranchCode()` (parser-driven, **branch segment only**, preserves prefix/year/sequence verbatim, null for non-canonical input, leaves `DG-LDK2-2024-TKM1` untouched) and `equivalentNumbers()`. Old-card compatibility: exact identity resolution widened to every spelling in `CrossBranchPatientLookupService` + `LegacyRmePatientResolutionAuditService` — **never** a second patient row. `LegacyRmeBranchAdmissionService` + `config/legacy_rme_rollout.php` canonicalize BOTH sides (allowlist, approved set, forbidden set, pilot scope, and the resolved code), so a stale environment cannot lock an approved branch out. `RmeBranchSeeder` matches every equivalent code before deciding a branch is missing, so it can never duplicate Telkomas (renaming stays the migration's job).

**Deliberately preserved (do NOT "tidy" these).** `LegacyRmeSourceRmNormalizer` transcribes the source Nomor RM **faithfully** — it recases but never canonicalizes, because the paper document really does say `TKM1` and published evidence must not claim otherwise; reachability comes from alias-aware matching downstream. `trx_clinic_visits.visit_number` (4 rows, `VIS-TKM1-…`) are **issued transactional identifiers** on completed visits, printed on paper already given to patients; nothing derives a branch from them and the generator already emits `TLK1`. `sys_audit_logs` (5 rows), `stg_legacy_patient_imports` (2 rows incl. raw/normalized payloads), published legacy evidence + its stored source RM/bytes/checksums, and terminal (COMPLETED/CANCELLED) waves — all untouched.
