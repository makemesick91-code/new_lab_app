## DOCTOR-PWA-WEBAUTHN-CREDENTIAL-REVOKE-CONTAINMENT-1 — revoking one credential contains exactly one session (2026-09-08)

Branch `feature/doctor-pwa-webauthn-credential-revoke-containment-1` (base `feature/sprint-26-phase-26-8-stabilization-closure-go-watch-no-go-report`, baseline `doctor-pwa-webauthn-kill-switch-1-go` @ `9d4779c1`, evidence commit `f286e976`; do NOT target main). **The source audit found the mechanism already correct, and no defect was manufactured.** `PROOF-BINDING-1` binds a session to `DoctorSessionProof::webAuthn($credential->id)` — a reference to one row, not to "this device has a credential" — and `EnsureDoctorDeviceSession` → `denySessionReason()` → `deviceProofDenyReason()` re-verifies it per request through `usableForDevice()`, which filters `whereNull('revoked_at')`; the Android branch returns before any WebAuthn state is read, and `revoke()` is terminal (early return if already revoked, no un-revoke path anywhere). **What was missing was the blast radius, not the containment.** The switch is consulted *before* the credential, so §14's evidence cannot speak for the credential path at all.

**Five gaps closed, all of them states the live ceremony creates.** `tests/Feature/DoctorDeviceWebAuthn/DoctorPwaWebAuthnCredentialRevocationTest.php` (12 tests / 91 assertions), every fixture dual-proof, every revocation through the **route an operator posts to** (`settings.doctor-devices.webauthn.revoke`) rather than a `revoked_at` write, because between them sit a policy check, a device-ownership check, a mandatory reason, a transaction and an audit write. (a) A **second usable credential on the same device** must not rescue a session bound to the revoked one — the existing suite only ever proved a credential on a *different* device does not, and recovery deliberately creates the same-device case. (b) Revocation leaves device and authorization `active` and conjures **no replacement** for either. (c) A revoked credential does not block re-enrolment and is **absent from `excludeCredentials`** — otherwise the one tablet whose credential you just withdrew becomes the one tablet that cannot be recovered. (d) A replacement never resurrects the old row. (e) The recovery login binds to the **new** credential id. Plus a flag-ON control, deny-code attribution (`webauthn_credential_not_usable`, with flag/device/authorization proven still good), pre-existing-Android survival, and pilot-scope isolation.

**Non-vacuity proven by two mutations.** Dropping `whereNull('revoked_at')` from `usableForDevice()` kills **6**; replacing `firstWhere('id', $credentialId)` with `first()` kills **2** — and the pre-existing suites catch that second mutation only incidentally (1 of 61, via "credential reference names nothing"), which is the measurement that shows the same-device gap was real. **The first mutation run also caught one of my own new tests passing vacuously:** the enrol helper was logging the doctor out, so the assertion was measuring the helper. Root cause: the test client has one session while the clinic has two browsers; both helpers now snapshot the doctor session, act as the operator, restore it verbatim and `forgetUser()`. Mutations reverted **by file copy** (never `git checkout --`), source restored byte-identical before any gate was run.

**Durable rules CR-1..CR-15:** a session belongs to the exact credential that authenticated it (CR-1) and is denied on its **next** protected request when that credential is revoked (CR-2); another usable credential on the same device does not rescue it (CR-3) and neither does an Android Keystore key on the same dual-proof tablet (CR-4); an `android_keystore` session established *before* the revocation survives untouched (CR-5); revocation mutates neither device (CR-6) nor authorization (CR-7) and is terminal for that row — recovery is a fresh registration, never an un-revoke (CR-8); the revoked credential must stay out of `excludeCredentials` or containment causes the outage (CR-9); a replacement satisfies the original policy in full (CR-10) and never clears `revoked_at` (CR-11); old sessions never migrate to it (CR-12); device revoke is not an acceptable substitute (CR-13); global enforcement stays false (CR-14); and the ceremony ends in an explicitly **verified** safe state plus a real ordinary doctor login (CR-15).

## DOCTOR-PWA-GLOBAL-ROLLOUT-READINESS-1 — measuring whether the whole fleet could be enforced, and finding that twelve doctors could not (2026-09-10)

**Status: NOT READY, and the tag is withheld because of it.** Fifteen active Doctor-role accounts, each linked one-to-one to an active doctor record, no orphans and no defensible exclusion — so the target population is all fifteen. **The gate that failed on success.** `android:phase4a-pilot-readiness` exited **1** on production and printed `PHASE4A_PILOT_PREPARATION=NOT READY` on a deployment where the pilot was working exactly as designed — it was written for a preparation sprint whose claim was "we shipped nothing armed", and §17 armed it on purpose with the owner's approval. §17 recorded the contradiction as a known limit; this sprint closed it. **Enforcement stopped being a boolean.** A boolean cannot separate an owner-approved three-doctor pilot from a clinic-wide lockout, and that conflation IS the defect. Four postures now — `off`, `bounded_pilot`, `global_rollout_readiness`, `global` — observed from the running state and compared against a declaration in `config/android_release.php` (`enforcement.expected_posture`), out of reach of a host for the same reason `global_permitted` and `pilot_cohort_maximum` are. **The declaration is a CEILING, not an equality:** the same reviewed code runs off on a developer machine, off in CI and armed on production, so demanding equality would either redden CI or force the declaration down to the weakest deployment and stop it auditing production at all. Enforcing MORE than was reviewed is what fails. `global_rollout_readiness` sits at the SAME strength as the pilot it describes — if measuring outranked the pilot, declaring readiness would itself be an activation.

**A second staleness, found while fixing the first.** `GLOBAL_ENFORCEMENT_ACTIVE=false` was printed by reading a hardcoded `false` out of the activation-boundary block.
