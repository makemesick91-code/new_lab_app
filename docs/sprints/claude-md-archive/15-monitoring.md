**Root cause.** Both verdict-producing monitors read a hardcoded `storage/logs/laravel.log`. That path was correct only by coincidence — production resolves `logging.default=stack → channels=[single] → .../storage/logs/laravel.log`. Flip `LOG_CHANNEL`/`LOG_STACK` to `daily`, or add a stack member, and the application writes errors elsewhere while the monitor keeps reading a file that has stopped moving → `logs=OK` on a failing system. **Reproduced first:** 3 negative controls (error in today's daily file / behind a `stack→[daily]` / in yesterday's file 30s after midnight) all returned `OK` against the old code and `WATCH` after.

**New `App\Services\Monitoring\MonitoringLogSourceResolver`** — sole authority for *which files carry this app's log events*; it does not parse lines or classify health. Reads `config('logging.*')`, **never `env()`** (production runs `config:cache`, where env is not the runtime authority). Expands `stack` recursively with cycle + depth guards; `single` → one file covering all history; `daily` → one file per calendar day intersecting the window, named by Monolog's `{filename}-{date}` applied to the **configured** path with day boundaries in `config('app.timezone')`. Unsupported drivers (syslog/stderr/Slack/custom monolog) are **reported, never dropped**. A `null` channel is exempt — detected by its `NullHandler` class, **not** by the channel being named `null` (the shipped `null` channel's driver is `monolog`). Rotated-file expansion is capped at 31 files (an unbounded `--since=365d` would otherwise open a year of files at 2 MiB each); hitting the cap marks coverage incomplete rather than answering from the part that fit.

**Both monitors share it.** `PilotPerformanceSnapshotService::collectLogSummary()` folds a source *set*: counts sum, statuses take the worse, timestamp extremes widen, coverage is the conjunction, and each source must be read back to its own required reach (window cutoff for `single`; later of cutoff and day-start for a day-file). `FoundationMonitoringStatusService::applicationLogSignal()` (MON-1) consumes the same resolver — it previously answered **GO** for a missing file. **The duplicate `config('foundation_monitoring.paths.laravel_log')` knob was retired**: a second declared path could disagree with the running logger and, being the one actually read, would have won silently and made this fix inert. Do not reintroduce it.

**Fail-closed contract.** Not OK when: no supported source configured; nothing readable actually read; an unsupported member sits in a monitored stack; a `single` file is missing; a present file cannot be opened (no fabricated byte count); any source is truncated short of its required reach; or the rotated-file cap bit. **The one tolerated absence:** a `daily` day-file may be missing when its directory was listable *and* the day is inside the channel's own `days` retention — nothing could have removed it, so "not there" is an observed empty day. **Deliberate supersession:** the previous sprint scored a missing file `OK` + warning; that cannot separate a quiet system from a relocated log, so absence is now **unverified (WATCH)**. The metric schema stays stable across verdicts (every key emitted, `null` for unmeasured) so dashboards keep parsing. Counting across sources can only **over**state severity (a stack writing one record to two files counts it twice), never understate — do not replace the sum with a max, which would demote a burst split across files.

**Security posture:** monitored paths come only from trusted config — no route or CLI flag accepts one, and the `log_path` seam on `collect()` is internal/test-only (pinned by a test). New metrics expose channel names + `basename()` only, never full paths; the MON-1 masked error excerpt is unchanged.

## MONITORING-LOG-TIMESTAMP-ROLLOVER-1 — an event's age comes from the timestamp the log wrote, not one the parser invented (2026-08-22)

Branch `feature/monitoring-log-timestamp-rollover-1` (base `feature/sprint-26-phase-26-8-stabilization-closure-go-watch-no-go-report`, baseline `monitoring-log-source-resilience-1-go` @ `a7622c7`). Doc `docs/sprints/monitoring-log-timestamp-rollover-1.md`; rule mirror `.cursor/rules/115-monitoring-log-timestamp-authority.mdc`. **Closes the Carbon date-rollover residual — `CODE_CHANGE_REQUIRED=true`, both a false green and a false WATCH were reproduced.** **No migration, no permission, no route, no schema, no runtime driver change; one file in `app/` changed.**

**Why it survived two sprints:** MONITORING-LOGS-WATCH-ROOT-CAUSE-1 deferred it on the written grounds that rollover *"only ever moves a timestamp later, so it cannot manufacture a false green"*. **That reasoning is wrong**, and the backlog entry told every later reader it was safe. `Carbon` rolls month `00` **backward into the previous year** (`2026-00-15` → `2025-12-15`) and day `00` backward into the previous month (`2026-08-00` → `2026-07-31`). Both the sprint doc and the CLAUDE.md entry are now corrected in place rather than left to mislead again.

**The defect, measured end-to-end.** `Carbon::parse()` is inconsistently permissive: it **throws** on `2026-13-01` / `2026-08-32` / hour `25` / minute `61` (correctly unageable) but silently **normalises** `2026-02-30`→`2026-03-02`, `2026-02-29`(non-leap)→`2026-03-01`, `2026-08-00`→`2026-07-31`, `2026-00-15`→`2025-12-15`. **FALSE GREEN:** on 5 Jan an `ERROR` stamped `[2026-00-15]` reported `historical=1, undated=0, parse=ok` — byte-identical to a genuinely old event — so it contributed nothing and the section could report **OK** while holding an error whose real date is unknowable. **FALSE WATCH:** on 2 Mar an `ERROR` stamped `[2026-02-30]` reported `fresh=1` and published `latest_fresh_error_at=2026-03-02T10:00:00+00:00` — a WATCH on an instant that never occurred, unclearable by fixing anything real. The fabricated date also anchored `oldest_scanned_event_at`, widening a window-coverage claim the scan had not earned. The audit additionally found the header's trailing `[^\]]*` segment honoured arbitrary PHP relative modifiers (`[… 10:00:00 -1 year]` → 2025), an **unbounded** age shift that still reported `parse=ok`.

**The fix (one method).** `extractTimestamp()` captures the literal calendar digits alongside the parsed value and requires the parse to reproduce them exactly (`$timestamp->format('Y-m-d H:i:s') !== $literal → null`), compared in the value's **own** timezone so explicit offsets stay honoured. It is a **faithfulness test, not a format whitelist** — everything that round-trips is accepted unchanged (Laravel `Y-m-d H:i:s` = `LogManager::$dateFormat`, what production writes; Monolog ISO-8601+offset; fractional seconds; offsets; real leap days), and only a value the parser had to *change* is rejected, into the **existing** unageable path that already fails closed (`undated>0` ⇒ WATCH, OK provably unreachable — `PilotPerformanceSnapshotClassifier:192-207`). It closes the relative-modifier class as a by-product. **Never replace this with a list of permitted formats:** a whitelist that guessed wrong would turn every real error into `undated` and cause a permanent, un-clearable WATCH storm.

**Boundary pinned:** `event >= window_start` (**inclusive**) — `now-24:00:00` is INSIDE, `now-24:00:01` is OUTSIDE. **Not changed on purpose:** timezones (`config('app.timezone')='UTC'`; log lines carry no offset so writer and reader share PHP's default by construction, and daily rotation uses the same value — everything already agreed, nothing was "normalised to WITA"); `ClinicalClock` stays unwired from monitoring; explicit offsets/tz names stay honoured (they are faithful instants, not corruption); Carbon mutability (every `subSeconds`/`subDays`/`startOfDay`/`setTimezone` in the stack is already `->copy()`-guarded — no immutability rewrite warranted).

**Recorded, NOT fixed (honest backlog):** ~~`oldest_scanned_event_at` can still be anchored by an injected *valid* ancient benign line (e.g. `[2020-01-01 00:00:00] production.DEBUG:`), converting a truncation WATCH into OK — a log-injection/coverage concern in a different subsystem needing its own reproducer~~ — **CLOSED 2026-08-23 by MONITORING-LOG-COVERAGE-ANCHOR-INJECTION-1. The residual was real, was reproduced end to end, and was a false green, not merely a metadata wobble**; `undated_error_like_count` cannot escalate past WATCH (fail-closed, but severity under-reports); `RestoreDrillEvidenceService::ageHours()` uses `strtotime()` on `completed_at`, same normalisation family, different subsystem (ROLL-5-1A evidence).

**Tests:** new `tests/Unit/Services/Monitoring/PilotPerformanceSnapshotTimestampRolloverTest.php` (29 / 75 assertions) — day/month/year/leap-day rollover, both false-green and false-WATCH directions, the relative-modifier class, the 24h boundary triple, UTC↔WITA display-vs-classification, future timestamps, coverage-anchor integrity, and negative controls for every real format. **Every test freezes the clock (`Carbon::setTestNow`)** — none depends on the real date, midnight, a month end or a year end. **Negative control (load-bearing):** the suite run against the pre-fix analyzer → **12 failed / 17 passed**; post-fix → **29 passed**. The 17 passing in both are the invariants, proving the fix changes nothing it should not. ## MONITORING-LOG-COVERAGE-ANCHOR-INJECTION-1 — log coverage is proven by the bytes actually read, never by a timestamp inside them (2026-08-23)

Branch `feature/monitoring-log-coverage-anchor-injection-1`, base `01d2870d` (`monitoring-log-timestamp-rollover-1-go`). Type `RUNTIME_FIX`. **No migration, no permission, no route, no schema, no runtime driver change.** Closes the residual the previous sprint recorded as honest backlog — and that residual was a **false green**, not a metadata wobble.

**The defect (reproduced by executing the code, not by reading it).** A source larger than the 2 MiB budget is read tail-only, so its **prefix** is skipped. Coverage was then decided by `$sourceCovered = ! $truncated || (Carbon::parse($oldest_scanned_event_at) <= $source->requiredCoverageFrom($cutoff))` — i.e. by the oldest event timestamp *inside the scanned tail*, on the unstated assumption that the file is strictly chronological. That made log **content** the authority over bytes the monitor never opened. Frozen clock `2026-08-22 12:00:00`, 24h window, a real in-window `pilot.ERROR` planted in the unread prefix: an all-ancient-`INFO` tail → `window_fully_covered=true`, `fresh=0`, **`logs=OK`**, `overall=OK`, reason *"No fresh error events within lookback window."*; the same file with **fresh** filler → WATCH. And the decisive one — fresh filler plus **one** injected `[2019-01-01 00:00:00]` line → back to **OK**. **Two files differing by a single line gave WATCH and OK.** The classifier was never at fault: `PilotPerformanceSnapshotClassifier` already returns WATCH for `!$windowFullyCovered`, and that flag is read only on the zero-count branch — it was handed a `true` it should never have been given.

**Reachability (mechanism verified; scope stated honestly).** Any line merely *starting* `[Y-m-d H:i:s…]` is an event header. Laravel builds `new LineFormatter(null, $dateFormat, true, true, true)` (`Illuminate/Log/LogManager.php:488`) — the third argument is `$allowInlineLineBreaks` — so a newline inside a **message or a context array value** becomes a real physical line. It is not needed — Monitoring must stay correct against syntactically valid content it did not expect, whatever the origin (operator, import, vendor error string, multi-process interleaving, restored/concatenated log, or a line written with an explicit past timestamp).

**Durable rules (116):** R1 coverage is a fact about the read, never about its contents — *an event cannot testify about bytes nobody read*. ## RESTORE-DRILL-TIMESTAMP-FAITHFULNESS-1 — Restore Drill evidence age is computed only from a faithful timestamp (2026-08-23)

Branch `feature/restore-drill-timestamp-faithfulness-1` (base `feature/sprint-26-phase-26-8-stabilization-closure-go-watch-no-go-report` @ `a51e536`, which is also `monitoring-log-coverage-anchor-injection-1-go` and was the live VPS HEAD; do NOT target main). ## MONITORING-UNDATED-SEVERITY-ESCALATION-1 — Unageable ERROR Evidence Carries Severity Weight (2026-08-23)

Branch `feature/monitoring-undated-severity-escalation-1` (base `feature/sprint-26-phase-26-8-stabilization-closure-go-watch-no-go-report`, baseline `restore-drill-timestamp-faithfulness-1-go` @ `09a02e3875654ea686a02d434f0b318229258958`; do NOT target main). Sprint doc `docs/sprints/monitoring-undated-severity-escalation-1.md`; rule mirror `.cursor/rules/118-monitoring-undated-severity-escalation.mdc`; rule 115 R9 superseded **in place** (old reasoning retained, not deleted). **No migration, no route, no permission, no schema, no runtime driver change; one method changed.**

**Root cause: truncated severity ladder — a decision defect, not a display defect.** Rule 113 R2 and rule 115 R9 pinned that an unageable ERROR may never read as OK. Both describe a **floor**; nothing anywhere asserted a ceiling, and no rung above the first was ever extended to the undated bucket. Reproduced against the unmodified classifier at the base SHA: `undated=1` and `undated=1000` both returned WATCH — magnitude ignored entirely. Consequence: **150 error events with valid timestamps → FIX; the identical 150 with corrupt timestamps → WATCH** (two severity levels bought by corruption in a date field). Mixed evidence understated too: `fresh=15, undated=100` (up to 115 in-window events) → WATCH, and `fresh=20, undated=1` → WATCH while `fresh=21` alone is INVESTIGATE. `UNDER_SEVERITY_REPRODUCED=true`; `FALSE_GREEN_REPRODUCED=false` — OK was already unreachable, so the defect was false *calm*, never a false green.

**The measured premise (not assumed):** `undated_error_like_count` and `fresh_error_like_count` are produced by the **same event-grouping pass** and carry the **same unit** — one error-like log event, verified 1:1 at n=1/20/21/150 by running the real analyzer over synthetic tails, with a double-count probe confirming an undated event lands in that bucket and no other. The buckets differ in whether the monitor can say *when*, never in whether an error happened. **Two axes kept separate:** error-existence confidence is equal; timestamp confidence is absent in one. The defect was collapsing the second into the first.

**Contract:** since the monitor cannot rule out that an unageable event falls inside the window, the fail-closed reading is that it does, so the counts are **summed onto the canonical in-window ladder** — `errorEvidenceCount = fresh + undated`; `0`→OK, `1..20`→WATCH, `21..100`→INVESTIGATE, `>100`→FIX. **Not a new contract:** the ladder's first rung was already applied (`undated > 0 ⇒ WATCH` is numerically identical to `fresh >= 1 ⇒ WATCH`); only the higher rungs were missing. Rejected on evidence: *independent worst-of* (understates `15+15` = up to 30 in-window events as WATCH — rule 113 R4's failure mode relocated) and *separate higher undated thresholds* (would discount evidence the monitor has no basis to discount — the exact false confidence this sprint removes). **Deliberately not done:** `criticalFreshCount` stays fresh-only — the analyzer tests CRITICAL_PATTERN only on ageable events, so there is no measured undated critical count and inventing one would assert severity never observed.

**Every change in the decision matrix is an escalation; nothing is downgraded.** Escalated: `0/21`→INVESTIGATE, `0/101`→FIX, `0/150`→FIX, `15/100`→FIX, `coverage-incomplete + 150`→FIX. Unchanged: all fresh-only rungs, `0/0`→OK, `0/1`→WATCH, `0/20`→WATCH, `5/5`→WATCH, the R4 pin (`150 fresh/crit 20/orphan 21`→FIX), orphan-only WATCH, coverage-incomplete WATCH, and missing/unreadable/unsupported source (fails closed **before** classification, so undated can never downgrade it). Monotonicity proven **exhaustively over a 9×9 count grid on both axes**, not at hand-picked points.

**Security — no new alert-DoS primitive.** Reaching the undated bucket requires three gates: well-formed Laravel header shape, a **failed** faithfulness round-trip, and `ERROR_PATTERN`. Measured: corrupt-date + `INFO` → 0; plain text containing `ERROR` → orphan, not undated; malformed bracket → orphan. So undated demands **more** structure than fresh, and forging N well-formed ERROR headers is *easier* and **already** reached FIX before this sprint — pinned by a test asserting the undated verdict is never worse than the valid-dated one at equal volume. `CLASSIFIER PRIMITIVE CONFIRMED`; `ATTACKER-CONTROLLED PRODUCTION PATH NOT ESTABLISHED` (no such path demonstrated, none claimed). **Lifecycle:** undated evidence cannot age out (no usable age) but clears when the line leaves the physically scanned tail via rotation; nothing is persisted, so no un-clearable state is created. Named residual: a parser regression would now produce a FIX storm rather than a WATCH storm — which raises the cost of breaking rule 115 R2, and does not license relaxing it.

**Downstream:** `pilot:performance-snapshot` JSON/weekly evidence now reflects undated volume (intended); `resolveExitCode` returns SUCCESS unless `--fail-on-watch` is passed, and **no repo script, deploy step, or CI job invokes the command**, so escalation cannot block a deploy. **MON-1 `applicationLogSignal` deliberately unchanged** — it counts `.ERROR:` tail *lines* with no timestamp/ageing concept, so it has no undated blind spot, and the two signals answer different questions (one authority per question; do not "unify" them). `SlowQueryAudit*` untouched. **Not changed:** timestamp parser/faithfulness, `MonitoringLogScanCoverage` physical byte-offset authority, `MonitoringLogSourceResolver` (single/daily/stack, fail-closed), fresh thresholds, critical escalation, lookback window, retention, 2 MiB budget, `overall_status = worst(...)`, analyzer metric schema.

**Independent adversarial review:** a reviewer extracted the real pre-fix class at the base SHA and ran a differential harness — **216,000-case production-domain grid: 0 false greens, 0 downgrades, 0 reason drift; 3,294,912-case monotonicity sweep: 0 violations**; no CRITICAL, no HIGH. Over non-negative inputs `errorEvidenceCount === 0` is *strictly narrower* than the old `freshCount === 0` gate, so the OK path became harder to reach, not easier. Two follow-ups **fixed in-sprint**: (1) **reason accuracy** — a mix (`fresh=5, undated=1`) reported "freshness is unknown", hiding positively-confirmed in-window events behind a corruption story, and "some carry unparseable timestamps" under-stated the all-undated case; the reason now has **three static-literal branches** (fresh-only / all-undated / mixed) with the fresh-only wording byte-identical; (2) **input robustness** — summing two variables lost the accidental immunity the single-variable zero test had, so a cancelling pair (`fresh=1, undated=-1`) would have read as no-evidence → OK; each term is now floored at zero independently (unreachable from the analyzer, whose counters only increment from zero, but a latent footgun the old shape lacked). One finding **accepted and documented**: the **persistence asymmetry** — a fresh alert self-clears by ageing, an undated one clears only on rotation, so escalation converts a self-clearing WATCH into a FIX that persists until the lines leave the scanned tail; accepted deliberately, since the alternative is discounting error evidence the monitor cannot date.

## RESTORE-DRILL-EVIDENCE-READ-STATE-1 — Restore Drill Evidence Read-State Contract (2026-08-23)

Branch `feature/restore-drill-evidence-read-state-1` (base `feature/sprint-26-phase-26-8-stabilization-closure-go-watch-no-go-report`, baseline `ci-monitoring-critical-token-coverage-1-go` @ `5478d72`; do NOT target main). Sprint doc `docs/sprints/restore-drill-evidence-read-state-1.md`; runbook §7.2 `docs/runbooks/roll-5-backup-restore-drill-runbook.md`; rule mirror `.cursor/rules/92-restore-drill-evidence-read-state.mdc`; manifest `.sprint/current.yml` (RUNTIME_FIX). **No migration, no permission, no route, no schema, no frontend change; ledger/RME/clinical untouched; production evidence never mutated and no live restore performed.**

**Root cause (reproduced on the base commit, not assumed).** `RestoreDrillEvidenceService` read evidence as `$raw = (string) @file_get_contents($found);`. `file_get_contents` returns `false` on failure, the cast turns that into `''`, and `''` is indistinguishable from a file that genuinely held nothing — so `json_decode` saw empty input and **every upstream fault was reported as "JSON tidak dapat diurai"**, including faults where not one byte was read. There was no `is_readable()` check anywhere in the path, and `locateEvidence()` skipped `filesize() === 0` candidates, so a zero-byte file was reported as *no file at all*. Twelve fixtures run against unmodified base code as uid 1000 (so `chmod 000` genuinely denies the read) produced four conflations: `EMPTY→ABSENT`, `UNREADABLE→INVALID_JSON`, `READ_FAILED→INVALID_JSON`, `VALID_JSON_NOT_OBJECT→INVALID_JSON`. **`FALSE_GO_REPRODUCED=false`** — every one of those states was already non-GO, so this is a state-integrity/observability defect, never a false-green one.

**Already known and accepted.** `tests/Feature/Cicd/CriticalGateWarningContractTest.php` carried a note that this service "casts a failed read to a string, so an unreadable evidence file reports 'invalid JSON' rather than 'unreadable'", judged acceptable because it still failed closed. The fail-closed half was correct and was re-measured; the half that does not hold up is that a vaguer reason is therefore harmless — it sends an operator to fix a document's format when the fault is a permission or an I/O failure. **That reasoning is superseded in place, in the file that carried it.**

**Fix.** New `App\Support\Foundation\RestoreDrillEvidenceReader` decides the read outcome once, before any content is interpreted: `absent | unreadable | read_failed | empty | ok`, with `contents` non-null only for `empty`/`ok` so a caller can never mistake *read nothing* for *read an empty document*. `false` is never coerced. Suppression (`@`) is warning-noise control only (the Critical Gate warning baseline is a declared `0`); the control flow is the explicit `=== false` check. The decode stage splits on `json_last_error()`: decoder rejection stays `invalid_json`; accepted-but-wrong-shape becomes `evidence_not_an_object` (both FAIL). New stable issue-code constants `ISSUE_ABSENT|EMPTY|UNREADABLE|READ_FAILED|INVALID_JSON|NOT_AN_OBJECT`, and every result now carries a machine-readable `details.read_state`.

**Deliberately NOT changed — the load-bearing decision.** `locateEvidence()` keeps its exact `is_file($abs) && filesize($abs) > 0` predicate. Letting a read fault fall through to the next candidate would have been strictly **more permissive** — a secondary path answering for a canonical file nobody could read. An existing-but-unreadable candidate therefore still blocks. The zero-byte case is instead detected by a separate `firstEmptyCandidate()` scan consulted only when no candidate was usable. **Measured differential across all 13 states: `READINESS_DELTAS = 0`** — every verdict preserved, only the reasons became true. Explicit asymmetric boundary: **zero bytes = no evidence recorded (WATCH); any bytes that are not valid evidence = corrupt evidence (FAIL)** — so whitespace-only stays FAIL exactly as at base.

**Durable rules:** (1) read state before parsing/validation; (2) a failed read is never empty content — no `(string) false`, no `?: ''`; (3) `invalid_json` means bytes were read and the decoder rejected them, never a filesystem fault and never a wrong-shape document; (4) successfully-read-empty ≠ read failure; (5) trust before freshness — an untrusted instant yields no age (RESTORE-DRILL-TIMESTAMP-FAITHFULNESS-1 preserved); (6) absent/empty/unreadable/read_failed/invalid_json/not_an_object/invalid-schema/unsafe/invalid-timestamp/future-timestamp/stale are all non-GO; (7) truthfulness must never buy permissiveness — changing a reason is allowed, moving a verdict is a separate explicitly-justified decision; (8) verify in production non-destructively — never mutate canonical evidence, never `chmod` it, never run a live restore to exercise a state (use `--path` with a throwaway file); (9) never guess Artisan flags on production.

**Verification.** Mutation control: reintroducing `(string) @file_get_contents($found)` fails **6** tests — the contract binds to the read boundary, not to message text. Real-filesystem `chmod 000` control skips (never silently passes) when the running user can read a `0000` file, with an injected-reader control covering the same state unconditionally. `READ_FAILED` is injected because a real I/O fault cannot be scheduled by a test — the state is real, only its timing is synthetic. Tests: new `tests/Feature/Foundation/RestoreDrillEvidenceReadStateTest.php` (24 passed / 110 assertions), declared in `config/ci_runner.php` `critical_gate_mandatory_suites` and **verified by execution** (`--list-tests`) to contribute 24 tests to the critical filter, so a rename can move its coverage but not delete it. `CriticalGateWarningContractTest` suppressed-read EXACT-SET inventory updated (service removed, reader added). **Gotcha:** that inventory is exact — moving or cleaning up a `@file_get_contents` without updating it fails CI by design, which is how this sprint's own change was caught.
