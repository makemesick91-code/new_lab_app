## REVISION-DOCTOR-PWA-WEBAUTHN-ONLY-ACCESS-1 — Stages 1–3 + verify-device bugfix (2026-09-19)

Branch family under base `feature/sprint-26-phase-26-8-stabilization-closure-go-watch-no-go-report` (do NOT target main). Sprint docs `docs/sprints/revision-doctor-pwa-webauthn-only-access-1-phase-0.md`, `…-stage-3-drill.md`, `docs/sprints/bugfix-doctor-pwa-webauthn-verify-device-no-feedback-2.md`; runbook `docs/runbooks/doctor-device-loss-rehearsal.md`; owner risk acceptance `docs/operations/doctor-device-estate-owner-risk-acceptance-pre-live.md`; rule mirror `.cursor/rules/93-doctor-pwa-webauthn.mdc` (**rules 74–85**). Programme intent: make the PWA the sole supported Doctor access channel with WebAuthn + trusted-device governance as the **server-side** boundary. **"PWA-only" is a PRODUCT ACCESS POLICY — `display-mode: standalone`, `navigator.standalone`, user-agent, installation state and sidebar visibility are NEVER authentication authority.** A crafted HTTP request for Doctor password login must still be denied by the server.

**Stage sequencing is authoritative and Android retirement never precedes Stage 1–3 proof:** Stage 1 canonical trusted-device proof abstraction → Stage 2 migrate consumers + break-glass → Stage 3 controlled acceptance + device-loss rehearsal → Stage 4 governed scope widening → Stage 5 Android retirement → Stage 6 closure.

**Stage 1 — the canonical predicate.** New `app/Modules/DoctorDevice/Services/DoctorDeviceIdentityProofPolicy.php`: `acceptable()` / `proof()` returning `PROOF_ANDROID_KEYSTORE` | `PROOF_WEBAUTHN_DEVICE_BOUND` | `PROOF_NONE`. It prefers an already-loaded `webAuthnCredentials` relation over a repository call (reports load the estate once and pin query counts) and applies the revoked filter itself, because the relation is unfiltered while the repository is not. It deliberately does NOT read `config webauthn.require_device_bound`.

**Stage 2 — 7 call sites migrated** across `DoctorDeviceBulkAuthorizationService` (×2), `DoctorGlobalRolloutReadinessService` (×2), `DoctorEstateResilienceService::isEligible()`, `DoctorFleetReadinessService` (×2). `DIRECT_ANDROID_CRYPTO_REQUIREMENT_FOR_GENERIC_PWA_ELIGIBILITY = 0`; 4 justified readers remain (3 Android-protocol, 1 reporting snapshot). **Why Android could not be retired first:** `cryptographically_verified` is written ONLY by Android enrolment and was read as a hard gate in 8 places — retiring Android first would make new PWA-only devices permanently unprovisionable. Break-glass shipped as `DoctorBreakGlassGrant` + `DoctorBreakGlassService`, consulted at BOTH `denyBrowserSessionReason()` (with `markUsed`) and `denySessionReason()` (no write). **The grant table keys on `user_id`, NOT `doctor_id`** — live proof: user 9 → doctor 17, user 18 → doctor 21; keyed on `doctor_id` it would have targeted a different person.

**Stage 3 — device-loss rehearsal PASS**, executed 2026-09-18 on the production pilot with drg Nisa (user 9 / doctor 17, LDK2). Break-glass granted 13:30:06, session reached 13:31:23, revoked 13:32:35, **already-open session thrown out on the next click** — a window capable of running to 14:30:06 was dead at 13:32:35, which is the single property the drill existed to test. Steps 2.2b (second doctor) and 2.6 (restore via tablet) **NOT EXERCISED** — the tablet was deliberately out of scope. Evidence producer `DoctorDeviceLossDrillCommand`: `--create-template` writes a `TEMPLATE`-marked placeholder the validator reports UNVERIFIED, `--outcome=passed` requires `--performed-by` AND `--confirm-performed`, and failed drills are recordable because a drill that went badly is evidence of the opposite thing.

**The verify-device defect and its fix.** On the SPN4 pilot tablet (`PHASE4A_PILOT_TABLET_02`, device id 3) Verify Device produced **no visible reaction** — five attempts, three client configurations, on a tablet holding a valid device-bound credential. Evidence: `POST /options` 200 every time, the assertion POST **never sent**, `Referer` matching the RP id, no Laravel errors. Root cause: `resources/js/doctor-device-webauthn.js` awaited `navigator.credentials.get()` with **no abort and no timeout**, so a ceremony that never settles left the `catch` unreached, no message rendered and the button disabled. Fixed with an `AbortController` + 60s `CEREMONY_TIMEOUT_MS` whose signal is actually passed to `credentials.get/create`, plus typed reason codes (`timeout`, `no_credential_or_denied`, `ceremony_cancelled`, `origin_not_trusted`, `device_state_invalid`, `unsupported`, `session_expired`, `options_rejected`, `network_unavailable`, `unexpected`) mapped to distinct Indonesian wording with the code shown as `(kode: …)`. `NotAllowedError` is deliberately NOT reported as "no credential registered" — the spec returns it for both a missing credential and a dismissed prompt precisely so a page cannot probe the estate, and a test pins that. **No server-side security changed.** Tests: `tests/js/doctor-device-webauthn.test.mjs` 47 pass, mutation-checked (removing `signal` → `not ok 8`).

**Real-device closure ceremony, 2026-09-19 — the assertion SUCCEEDED.** On `PRODUCTION_HEAD=2813fc10` / tree `e9552b07`, bundle `app-CsockFtp.js` (104,320 bytes, server-verified over HTTPS), drg Karmila (user 18 / doctor 21, `DOC-SPN001`) on device 3: `POST /doctor-device-webauthn 302` at **00:53:04 UTC (08:53 WITA)** — the assertion that had never once appeared in five prior attempts; `last_used_at` moved `2026-09-09 → 2026-09-19`. Single-session PASS (second login at 00:57:18 bounced to `/login`, created no lease, `FIRST_SESSION_EVICTED=NO`). Logout PASS (lease 21 released 00:58:38). Break-glass not used. Child GO tag `bugfix-doctor-pwa-webauthn-verify-device-no-feedback-2-go`. **Honest limits:** because verification *succeeded*, the error-feedback path was never exercised on hardware (proven by mutation-checked unit tests only); **Defect B is RESOLVED with `ROOT_CAUSE=UNVERIFIED`** — an abort signal cannot make a failing assertion succeed, and stale cached client code is a hypothesis, not a diagnosis.

**DURABLE RULES ESTABLISHED (mirror `.cursor/rules/93-doctor-pwa-webauthn.mdc` 74–85).** (1) Android Keystore proof and WebAuthn proof are **separate mechanisms sharing no code path** — `DoctorAppLoginService` holds 0 WebAuthn references, `DoctorDeviceWebAuthnLoginService` holds 0 Keystore references. (2) **Android success is NOT evidence the PWA works**; "the pilot is live" was true and irrelevant for ten days. (3) **Android retirement is blocked** until a real-hardware WebAuthn assertion AND the resulting PWA session are proven — a hard dependency, not a preference. (4) **Verify Device must never silently no-op**: every ceremony ends in success or a visible deterministic message, and every browser-side ceremony is bounded by an abort signal (the WebAuthn `timeout` member is only a hint). (5) Application time authority is **UTC**; clinic-local timestamps must say **WITA (UTC+8)**. (6) `single_active_session=true`, `branch_lock=false`. (7) **Stage 4 stays unauthorized while a prerequisite measures FAIL.** (8) `spare_device_available_per_branch` stays **FAIL** until the estate is re-measured — the owner's pre-live risk acceptance sits beside that measurement, never on top of it. (9) **Controlled pre-live evidence is not real-world operational proof.** (10) **`webauthn:readiness` VERDICT=ARMED means configured, not proven live** — it is a flag plus a `COUNT(*)`; it reported ARMED daily while the browser leg was dead. Carried forward as `FIX-DOCTOR-WEBAUTHN-READINESS-LIVE-PROOF-1`.

**Posture unchanged by all of the above:** `device_loss_runbook_rehearsed=PASS` · `spare_device_available_per_branch=FAIL` (blocks activation) · `ACTIVATION_PREREQUISITES=FAIL` · `authorizes_activation=false` · scope `pilot [9,15,18]` · `global_permitted=false` · `GLOBAL_ENFORCEMENT_ACTIVE=false` · `ANDROID_DOCTOR_AUTH=RETAINED` · **STAGE_4_AUTHORIZED=NO**.

## DOCTOR-DEVICE-GUIDED-REGISTRATION-WORKFLOW-1 — Pendaftaran Device Dokter (2026-09-21)

Branch `feature/doctor-device-guided-registration-workflow-1` (base `feature/sprint-26-phase-26-8-stabilization-closure-go-watch-no-go-report` @ `e713f44b`; do NOT target main). Sprint doc `docs/sprints/doctor-device-guided-registration-workflow-1.md`; rule mirror `.cursor/rules/163-doctor-device-guided-registration-workflow.mdc`. Seven-step guided workflow at `/settings/doctor-device-registration` (`settings.doctor-device-registration.*`) for bringing a new clinic tablet into service — operated by authorized administrative users, **not** doctor self-registration. **No migration, no new permission, no seeder/role change, no JS/CSS, no production flag change; KTP/NIK not applicable; no credential material rendered.** **A GUIDE over the existing surfaces, never a second implementation:** steps 1/2/3 post to the existing `settings.doctor-devices.store|.update|.webauthn.options|.webauthn.store|.webauthn.revoke|.approve-registration` routes with their existing policies; the **only new mutation in the feature** is step 4 `settings.doctor-device-registration.doctors.store`. **Two parties stay two parties (D11 preserved):** `register_doctor_devices` (Supervisor RME) files a tablet, `manage_doctor_devices` (Super Admin) enrols its credential and admits it into service — the workflow is SHARED, not single-operator, and renders "Menunggu Super Admin" where the actor cannot act (presentation only; the route layer AND the policy both still refuse). **Step 4 files, never approves:** calls the existing `DoctorDeviceAuthorizationService::resolveOrRequest()` with `SOURCE_ADMIN`, which can only ever produce `STATUS_PENDING`; approval stays in Approval Device Dokter behind `manage_doctor_device_authorizations`. New `DoctorDeviceAuthorizationPolicy::requestForDevice` deliberately shares that permission with `decide` (a holder could already approve any pending row — the invariant is enforced at the WRITE, not at the permission). Sidebar: **Pendaftaran Device Dokter** under Master Data beside Device Dokter; **Approval Device Dokter stays a top-level operational group** (a daily queue must not sit behind a security-administration screen). **No `wizard_status` column and there must not be one** — every step is derived from existing security truth (device row / credentials / status / authorizations / live proof / readiness), so a completed step **un-completes itself** when the credential behind it is revoked (pinned by test). Return-to-workflow is a **boolean** `registration_workflow`, never a URL/path/route name (no open redirect on a device endpoint). New: `DoctorDeviceRegistrationWorkflowController` (thin), `DoctorDeviceRegistrationWorkflowService` (derives step state, holds no security truth), `DoctorDeviceRegistrationReadinessService` (device-scoped projection), `DoctorDeviceCredentialUsabilityPolicy`, `StoreDoctorDeviceAuthorizationRequest`, `ReturnsToRegistrationWorkflow`, `x-doctor-device-registration-shell` + 10 views.

**GLOBAL SERVICE DISABLED != DEVICE DEFECT — the canonical readiness decision for this sprint.** `DoctorAppLoginGate` refuses every WebAuthn proof while the estate-wide master switch `doctor.pwa_webauthn_device_login` is off, so an earlier draft reported a perfectly provisioned tablet as `NO_INVALID_DEVICE_STATE = FAIL` / `gate_refuses_a_provisioned_path` — a device defect for a reason that had nothing to do with the device and could not be fixed from that page. Locked behaviour, **two rules that are one decision**, both pinned by tests (and both proven non-vacuous by mutation): **(a)** with the flag OFF the device-specific checklist MUST NOT report a device failure — the gate-agreement check returns **`UNVERIFIED` carrying the real reason `webauthn_login_disabled`**, never `FAIL` and never `FINDING_GATE_DISAGREES`, while device active / not revoked / approval / credential active / user verification / device binding / doctor authorization all continue to report their own true state (all PASS for a healthy tablet); **(b)** the device still MUST NOT be declared clinically ready — `UNVERIFIED` is not a pass, the verdict stays `NOT_READY`, step 7 redirects to readiness and "READY FOR CLINICAL USE" is never rendered. (a) governs the REASON shown to the operator (do not send them to re-enrol a healthy tablet); (b) governs the VERDICT (do not promise a tablet works when the capability it needs is off). Fail-closed is deliberate. Changing either half without the other reintroduces exactly one of the two failure modes. **The remedy for a NOT_READY board caused by this is an estate posture decision about the flag, with its own change process — never an edit to this checklist and never a production flag flipped to make a screen go green.**

**Also fixed here:** (1) the board built the estate-wide `DoctorWebAuthnLiveProofService::report()` **once per device row** (20 tablets → 20 full estate scans); now memoised per request so every row is judged against ONE snapshot — pinned at **exactly one** build (reports 3 without the fix; a ceiling would pass for a duplicate). (2) The credential-usability chain was private to `DoctorGlobalRolloutReadinessService`; extracted to `DoctorDeviceCredentialUsabilityPolicy` which the fleet engine now delegates to (behaviour-neutral, verified by that engine's own 41 existing tests) — the `REASON_*` vocabulary deliberately stayed on the fleet engine, since two names for one refusal is the same drift in a different disguise. Device-scoped readiness **reuses** those REASON_* constants + `DoctorDeviceIdentityProofPolicy` + `DoctorWebAuthnLiveProofService`'s PASS/STALE/NEVER_PROVEN/UNVERIFIED classification; it re-derives nothing, evaluates **every** gate with no early return (so revoking a credential / device / authorization each fails its OWN gate while the others stay PASS), and writes nothing. Step 5 has **no control that can record a pass and no route that could** — the verdict comes from audit rows written by the login path itself, attributed to the device the assertion was performed on. Tests: `tests/Feature/DoctorDevice/DoctorDeviceRegistrationWorkflow{Access,Steps,Readiness}Test.php` (88; named to match the existing `DoctorDevice` CI critical-gate token) — incl. a proof performed on another tablet, a credential re-pointed at this device, stale vs unmeasured freshness, and hand-typed-URL mutation denial asserted at the DB level.
