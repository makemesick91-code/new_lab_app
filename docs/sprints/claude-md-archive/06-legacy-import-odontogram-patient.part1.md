## LEGACY-ODONTOGRAM-NATIVE-REFERENCE-CUTOFF-1 — an empty odontogram placeholder is not clinical evidence for the archive cutoff (2026-08-22)

Branch `feature/legacy-odontogram-native-reference-cutoff-1` (base `feature/sprint-26-phase-26-8-stabilization-closure-go-watch-no-go-report`, baseline `post-rme-odontogram-stabilization-1-go` @ `9aa45a8`; do NOT target main). Sprint doc `docs/sprints/legacy-odontogram-native-reference-cutoff-1.md`; rule mirror `.cursor/rules/111-legacy-odontogram-native-reference-cutoff.mdc`. Settles the residual POST-RME-ODONTOGRAM-STABILIZATION-1 deliberately left open. **No migration, no route, no permission, no schema change; no native odontogram row deleted/edited/backfilled; no auto-import/auto-publish/migration batch; Legacy Odontogram stays at rest.**

**The defect.** `LegacyOdontogramNativeReferenceRepository` decided "this patient has a native odontogram" from bare row existence (`->whereHas('odontogram')`), so a row charting nothing counted as clinical evidence. **The cutoff acts in TWO directions** from one `resolve()` call: an eligibility **GATE** (`null` ⇒ `CODE_PATIENT_HAS_NO_NATIVE_ODONTOGRAM`) and a chronological **BOUND** (strictly earlier). A contentless placeholder therefore both opened the gate on evidence that does not exist and drew the bound on a date where nothing was charted. Under a narrowing predicate the two directions move **opposite** ways — always state both.

**Production read-only impact** (`asia_dental_lab_pilot`, PG 16.15, every session under `SET default_transaction_read_only = on`): 32 in-scope rows → **31 meaningful / 1 empty**; 15 patients with native rows → **14 meaningful / 1 empty-only**; `cutoff_moves_LATER` = 0; `WOULD_BECOME_ELIGIBLE_AFTER_FIX` = **0**; `BLOCKED_BY_MEANINGFUL_NATIVE` **14 before == 14 after**; delta **−1** (patient 45, whose sole odontogram is a `draft` with `NULL` payload on a visit with no medical record). **The brief's premise was inverted by the evidence** — an empty row is the only thing that can *open* the GATE, so on the gate direction ignoring it can only refuse more. That is NOT a general monotonicity guarantee: on the BOUND direction, dropping a patient's *earliest* row moves the bound LATER and **widens** the window (pinned by test, clinically correct — nothing was charted on the placeholder's date). `cutoff_moves_LATER = 0` is a measurement of today's data, not a structural property. Archive at rest (0 imports, 0 records), so nothing published was retroactively invalidated.

**Measurement error, caught and retracted.** The first pass used `jsonb_typeof(payload->'teeth')='array'` and reported 0 meaningful / 32 empty / all 15 patients empty-only. **`teeth` is a JSON OBJECT keyed by FDI number, never a list**, so the array test was false everywhere and mis-classified 31 rows of real charting as empty. Caught because the same output self-contradicted (`payload_empty_teeth = 0` while claiming all rows empty). **Verify the payload shape before trusting any count; contradictory numbers in one result mean the predicate is wrong.**

**The predicate already existed** — `private OdontogramService::hasRecordedTeeth()`, reachable only by Patient Odontogram History, while the cutoff counted row existence: two answers to one question. This sprint invented no third. Changes: `Odontogram::hasRecordedTeeth()` promoted onto the model (**the one definition**, beside `dmftCounts()` which reads the same payload); `OdontogramService` delegates (behaviour unchanged); the cutoff repository now requires content via the portable SQL half `whereNotNull('tooth_map_payload')` + the canonical PHP predicate, earliest-first with early exit via `lazy()`; interface contract restated. A charted tooth counts **regardless of status, `normal` included** — treating real content as empty erases a boundary, treating a sparse chart as content only keeps one; **when in doubt keep the boundary**. **Content, not workflow status** — 29 of 32 production rows are `finalized`, so a status shortcut would have been wrong.

**PostgreSQL portability (load-bearing).** `tooth_map_payload` is `jsonb`; comparing it to a string is a hard PG error (no `jsonb = text` operator) that SQLite tolerates — it would pass every local test and 500 in production. Only `whereNotNull` is portable in SQL; `{"teeth": {}}` and a missing `teeth` key are settled in PHP. **`whereJsonLength()` is forbidden here** — it compiles to `jsonb_array_length()` on PG, which errors on a JSON object.

**Test-fixture trap.** `OdontogramFactory` defaults `tooth_map_payload` to `NULL`, so `lodoNativeOdontogram()` had been manufacturing exactly the placeholder the cutoff must ignore — every pre-existing cutoff test asserted against a row with no chart. The helper now charts a tooth in the real production shape; new `lodoEmptyNativeOdontogram()` covers the contentless case. Tests: new `tests/Feature/LegacyOdontogram/LegacyOdontogramNativeReferenceCutoffTest.php` (19). **Negative control: 9 of 19 failed before the fix, 10 already passed** (the meaningful-data protections). `tests/Feature/LegacyOdontogram/*` already reaches CI via the `LegacyOdontogram` alternative in the `--filter=` of both critical-gate variants — no workflow change needed (verified, not assumed).

## FEATURE-LEGACY-IMPORT-HUB-1 — Legacy Import Hub: one home, one ceiling (2026-08-27)

Branch `feature/legacy-import-hub-1` (base `feature/sprint-26-phase-26-8-stabilization-closure-go-watch-no-go-report`; do NOT target main). Baseline `fix-rme-print-remove-patient-visit-duplicate-1-go` @ `5abd4ac`, tree `9496904` — verified exact-match against the deployed production HEAD before any edit. Sprint doc `docs/sprints/feature-legacy-import-hub-1.md`; rule mirror `.cursor/rules/128-legacy-import-hub.mdc`; manifest `.sprint/current.yml` (MODULE_SPRINT, LegacyImport).

**What already existed, and was NOT rebuilt.** Three legacy importers, built at different times, each complete on its own terms: **Legacy Patient** (Sprint 62.3, `settings.patients.import.*`, CSV → staging → preview → commit, gated `manage patients`, no feature flag), **Legacy RME** (LEGACY-RME-PDF-1A..ROLL-4, `settings.rme.legacy-imports.*`, five named permissions, flag `rme.legacy_pdf_archive`) and **Legacy Odontogram** (FIX-04b, `settings.rme.legacy-odontograms.*`, its own five permissions, flag `rme.legacy_odontogram_archive`). Two lived under *Master Data RME*; Legacy Odontogram had **no sidebar entry at all**. Not one line of any importer's validation, branch resolution, review, publish, void or read path changed.

**What is new — exactly two things.** (1) `ops_legacy_import_daily_quotas` and `LegacyImportDailyQuotaService`: **100 accepted records, per branch, per clinical day, per import type**, enforced through one code path in all three importers. (2) `Import Data Legacy` — one sidebar group (Ringkasan + the three uploads) and the read-only landing page `settings.legacy-imports.index`. The two legacy entries were MOVED out of *Master Data RME* (and that group's `@canany` lost the two legacy-RME permissions, which would otherwise open an empty group for a legacy-only operator).

**The ceiling, word by word.** **ACCEPTED** — charged inside the transaction that writes the record, so a refused upload / failed validation / duplicate / error row / rolled-back transaction consumes nothing and needs no compensating write. **BRANCH** — always server-resolved (archives: the branch-code segment of the Nomor RM; Patient: the row's required-and-strict `Cabang` column); a request-supplied branch is never the authority. **CLINICAL DAY** — `ClinicalClock`, never `config('app.timezone')`, which resolves to UTC in production and would roll the quota over at 08:00 WITA. **IMPORT TYPE** — counted separately; a full RME quota does not touch Patient or Odontogram. `NULL` declines to limit, `0` admits nothing, and a value above `max_declarable_daily` (500) is **clamped** with the hub saying so.

**Where each importer is charged.** RME and Odontogram: one staged document, inside `createFromUpload`'s transaction. **Legacy Patient: one COMMITTED patient row, inside `commit`'s transaction, reserved AFTER the rows are known** — staging is not acceptance (a staged batch writes nothing to `mst_patients` and can be discarded), and reserving late means a row the RM/KTP re-check skips costs nothing. A multi-branch batch is **all-or-nothing**. A **retry** re-queues render work for an already-charged document and is never charged again; a **re-commit** of a committed batch is a no-op. **Rollback deliberately does NOT refund** — a compensating write can itself fail, and a ceiling's safe direction is to under-admit.

**Composition, never replacement.** The ROLL-4 wave/branch quota is UNCHANGED. It answers a different question — how much may this WAVE take today across every branch enrolled — that the hub ceiling cannot express. Both apply, the tighter wins, neither can widen the other. **Never delete the wave quota to "consolidate".**

**Lock ordering — do not invert.** Legacy RME takes two locks; `createFromUpload` is the single site that takes both and takes **the hub bucket first, always**. Both order by `branch_id`; `reserveMany` sorts branch ids before locking. A future caller needing both must keep this order or the two form a cycle.

**Concurrency, proven not asserted.** SQLite compiles `lockForUpdate()` to nothing, so the SQLite suite — correct as it is — cannot prove the property that matters. `LegacyImportHubConcurrencyTest` runs against **PostgreSQL 16.14** (production major) and **skips loudly** elsewhere. It also cannot use `RefreshDatabase`: that trait never commits, so a second session sees no row, and `FOR UPDATE NOWAIT` on an invisible row raises nothing and would report "not locked" whether or not the lock existed — a false green on the one property the file exists to prove. It drives the real service over a connection `RefreshDatabase` does not manage, and asserts the probe CAN see the row when unheld so the lock assertion cannot pass for the wrong reason. 4 passed.

**Migration.** One additive table, `UNIQUE(import_type, branch_id, quota_date)` with every component NOT NULL (PostgreSQL treats NULLs as distinct in a unique index — a nullable component would silently permit two buckets for one day, each below the ceiling). No column altered or dropped, no backfill.

**Authorization.** The hub accepts the union of the three capabilities' view permissions and grants **nothing**: an actor holding only `manage patients` reaches the hub and still gets 403 on both archives. Branch scope = governance tier (any archive review/publish/void permission) sees the whole RME set, anyone else sees only their server-resolved branch, and only when RME-enabled; MAIN yields none. A forged `?branch_id=` changes nothing. **No permission created, widened, or granted to a new role.**

**Mutation testing — and the one that survived.** Ten mutants; nine killed immediately. **M6 (hub route's permission middleware deleted) SURVIVED**: the controller's own `abort_unless` re-check kept the *outcome* correct while a *layer* was removed, so every behavioural test stayed green. Gap closed with a test that pins the middleware list itself; M6 now killed. **Durable lesson: when a controller re-checks what middleware enforces, the middleware needs its own assertion — behavioural tests cannot see a deleted layer.**

**CI selection.** `LegacyImportHub` added to the NSF-R011 critical filter in **both** runner variants (they must stay identical), AND the quota/integration/surface suites declared in `config/ci_runner.php` `critical_gate_mandatory_suites` — a control that exists but is never selected is not a control, and the mutation run showed each importer's unwiring was caught ONLY by the integration suite. The concurrency suite is deliberately **not** declared mandatory: it can only ever skip on CI's SQLite, and a declared always-skipping suite reads as evidence it is not.

**Green.** `tests/Feature/LegacyImportHub` 53 passed / 4 skipped / 146 assertions (SQLite); concurrency 4 passed (PostgreSQL 16.14); `Cicd|CiMonitoring|CriticalToken` 286 passed. Legacy imports still create no clinic visit, medical record, odontogram, invoice, payment, prescription, lab order or SATUSEHAT resource.
