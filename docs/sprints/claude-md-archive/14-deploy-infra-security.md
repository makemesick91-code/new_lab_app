## INFRA-SEC-ENV-1 — Production Secret File Permission Hardening (2026-08-15)

Branch `feature/infra-sec-env-1-production-secret-file-permission-hardening` (base `feature/sprint-26-phase-26-8-stabilization-closure-go-watch-no-go-report` @ `2ffe00c`; do NOT target main). Sprint doc `docs/sprints/infra-sec-env-1-production-secret-file-permission-hardening.md`; runbook `docs/runbooks/production-secret-file-permissions-runbook.md`; rule mirror `.cursor/rules/100-production-secret-file-permission-hardening.mdc`; manifest `.sprint/current.yml` (SECURITY_FIX). **No migration, no permission, no route, no application runtime change, no clinical side effect.** **Finding:** the production environment file at the app root was `root root 0644` — **world-readable** on a host shared with a co-tenant application (`aish-pos`) and a `postgres` shell account. **Root cause: no deploy step had ever asserted a mode on it** — `deploy-vps.sh` hardened only `storage`/`bootstrap/cache`; the file was created once by hand under the default `umask 022` and kept `0644` forever. Existing gates all checked *writability for the runtime user*, never *unreadability for everyone else*, which is why none caught it (an absent invariant, not a regression).

**Approved state (derived from the real runtime, NOT assumed): owner `root`, group = PHP-FPM runtime group (`www-data`), mode `0640`.** **`0600` is wrong here and would cause a silent total outage:** `deploy-vps.sh` rebuilds caches **as the PHP-FPM runtime user** (`as_runtime php artisan config:cache`, from FIX-LOGIN-REDIRECT-RUNTIME-PERMISSIONS), and phpdotenv's `safeLoad()` **swallows a permission error and returns an empty environment** — so an unreadable file silently yields a config cache with an empty application key and empty DB credentials, with no error. Secret-bearing backups (`.env.bak*`/`.env.backup*`/`.env.save*`/`.env.old*`/`.env.orig*`) → `0600`; `.env.example` untouched.

**Shipped:** new `scripts/harden-secret-permissions.sh` (idempotent `apply`/`verify`; never prints contents; never creates/edits a secret file; never recursive-chmods the tree; fails closed on a symlinked secret file; detects named-user/group read ACLs when `getfacl` exists; `chown` only as root so it is testable unprivileged). `deploy-vps.sh` hardens **early — before it sources the file** and before the runtime user rebuilds the config cache — then re-asserts + `verify`s late, aborting with `NOT GO`. `rollback-vps.sh` re-asserts the same invariant. **Durable regression protection:** `harden-secret-permissions.sh` is a **required marker** in `config/deployment_rollback.php` for BOTH `deploy_expectations` and `rollback_expectations`, so `foundation:deployment-rollback-check` (runs in CI **and** inside every deploy) fails if the call is ever removed. `.gitignore` → `.env.*` + `!.env.example`.

**Known residual, deliberately NOT claimed as closed:** the co-tenant `aish-pos` FPM pool runs under the **same `www-data` account**, so a file mode cannot stop same-UID read. `0640` closes `postgres` and every other local account; closing the co-tenant needs a dedicated runtime account (own FPM pool user + queue worker `User=` + `storage`/`bootstrap/cache` ownership) — a separate sprint, out of this scope. **Gotcha for that future sprint:** `deploy-vps.sh` resolves `RUNTIME_USER` by grepping **all** FPM pool files and taking `head -1`; with two pools that only works while both declare `www-data` — make it pool-specific first.

**Gotchas:** (1) `release_evidence.forbidden_patterns` contains the literal `.env`, and ENT-15's `EnterpriseDocumentationScanner::sensitiveContentPosture()` applies it to **registered** runbooks + the policy doc — so the new runbook is deliberately **NOT** added to `config/enterprise_documentation.php` `mandatory_runbooks` (registering it without rewording would fail `foundation:enterprise-documentation-check` in CI and on deploy). (2) A fresh git worktree has no local env file, and phpdotenv's suppressed read makes **every** test report a PHP warning — including untouched pre-existing tests; create a local gitignored env file (or expect warnings). (3) The deploy runner `bash`-buffers `deploy-vps.sh`, so the deploy that *introduces* a script change runs the OLD body — the new hardening therefore takes effect on the **next** deploy, which is why enforcement was proven with a second deploy rather than assumed.

**SECOND FINDING (same deploy path, larger blast radius): `storage/app/backups/` held **175 database dumps at mode 0664 — world-readable**, each a full `pg_dump` of the clinical database (patients, KTP/NIK, records, invoices); `runuser -u postgres -- test -r` confirmed an unrelated account could read them. Same root cause (`pg_dump > file` under the deploy user's `umask 022`, then `normalize_runtime_ownership` sets every storage file to `0664`). Fixed **`other`-bits-only** (`0664`/`0644` → `0640`, owner/group untouched) so root (backup-verify/restore/rehearsal/evidence) and the runtime user (ENT-7 dev-console backup listing) keep the exact access they had and only unrelated accounts lose it — cannot break the ENT-11 storage contract or ENT-12 backup/DR. `deploy-vps.sh` and `rollback-vps.sh` also `chmod 0640 "$BACKUP"` immediately after `pg_dump` to close the creation window.

Tests: `tests/Feature/Deploy/SecretFilePermissionHardeningTest.php` (25 — functional runs of the real script against synthetic `APP_KEY=fake-test-value` fixtures in a private 0700 temp dir: 0640/0600 accepted; 0644/0666/0660/0664/0604/0646 rejected; apply converges + idempotent; backups forced 0600; example file untouched; wrong owner/group rejected; symlink fails closed; missing file creates no replacement; output never contains a fixture secret; plus deploy/rollback/ENT-11/gitignore contract). Green: Deploy dir 38 passed/109 assertions; `Ent11DeploymentRollbackAutomationTest` 12 passed/115; `Ent10|Ent12|Ent15|SafeCiRuntimeControl` 54 passed/519; pint + `git diff --check` clean; `bash -n` ×3 + `shellcheck -S warning` clean; CICD-CTRL-1 classifier → `unknown_high_risk` (all gates run). Deploy: **no migration, no seed**; post-deploy verify with `bash scripts/harden-secret-permissions.sh verify --owner root --group www-data`.

**Production finding (srv1730088, Ubuntu 24.04.4, measured not assumed):** DaengtisiaMS ran on the **distribution default `[www]` pool** (PHP 8.3) as `www-data` uid 33; the co-tenant **aish-pos** ran its own pool (PHP 8.5, own socket) *also* as uid 33; the queue worker and `daengtisiams-pilot-snapshot.service` were `www-data` too. Same uid ⇒ a file mode cannot stop the co-tenant reading the secret or `storage/app/private` (lab evidence, patient documents, legacy imports, KTP scan staging). `daengtisiams` user/group did not exist; no ACLs anywhere (`acl` package not installed, no mode string carries `+`). Two old `backups/*.sql` at the app root were `0644 root:root` (world-readable clinical dumps) — hardened to `0640 root:root`.

**Second, independent defect (the one the prompt predicted):** `scripts/deploy-vps.sh` resolved its runtime user with `grep -r '^user =' /etc/php/*/fpm/pool.d/ | head -1`, then a process-table guess, then `[ -n "$RUNTIME_USER" ] || RUNTIME_USER="www-data"`. The glob spans **every PHP version incl. the co-tenant's 8.5 pool**, so `head -1` is a directory-walk race — once DaengtisiaMS got a dedicated pool this could resolve the **co-tenant's** identity and chown DaengtisiaMS's runtime to it. All three mechanisms guess; a guess that lands on a shared account is the vulnerability itself.

**Built:** (1) `deploy/runtime-identity.conf` — the single shell-sourceable authority (`DMS_RUNTIME_USER=daengtisiams`, `DMS_FORBIDDEN_RUNTIME_USERS="root www-data nobody daemon postgres"`, pool/socket/units/writable/immutable/private path sets, `DMS_SECRET_OWNER=root`); no secrets, committed. Resolution is **fail closed, no fallback** (`exit 2` on missing authority / undeclared / forbidden identity / missing account / primary-group mismatch). (2) `deploy/php-fpm/daengtisiams.conf` — dedicated pool on `/run/php/php8.3-fpm-daengtisiams.sock`; pm sizing at parity with the `[www]` pool it replaces and **no `php_admin_value` limit declared** so `php.ini` (`upload_max_filesize`/`post_max_size`, which the Legacy RME PDF path depends on) is inherited unchanged — identity changes, behaviour does not; `clear_env = yes`, `security.limit_extensions = .php`. (3) `scripts/provision-runtime-identity.sh` — idempotent, **dry-run by default**, `--apply`/`--rollback`; creates the system account (no password/home/login shell, refuses to co-opt a pre-existing interactive account), installs the pool, validates `php-fpm8.3 -t` **and** `nginx -t` before any reload, cuts over inside `php artisan down` with an EXIT trap that lifts maintenance even on failure, retires the default `[www]` pool, rewrites **only** `fastcgi_pass` in place (preserving the `listen 80 default_server` that keeps the app reachable on this shared host), moves ownership of the writable set, strips world bits from private storage, delegates the secret group to the **INFRA-SEC-ENV-1 helper** (never chmods a secret itself), installs the units, and rebuilds the cache **as** the runtime user. Never runs a DB command; never `chown -R` the checkout. (4) `scripts/verify-runtime-isolation.sh` — read-only verifier proving identity/least-privilege/pool/socket/nginx/units/secret/writable/source-immutability/private-storage plus a live `runuser` **co-tenant denial** proof; `--require-host` turns "could not inspect" into FAIL so production never reports GO on unseen evidence.

**Wiring:** `verify-runtime-isolation.sh` and `chown -R "${RUNTIME_USER}:${RUNTIME_GROUP}"` are **required markers** in `config/deployment_rollback.php` for BOTH deploy and rollback, so removing either fails `foundation:deployment-rollback-check` in CI and on the VPS — the durable protection, not a one-time chmod. **Contract evolution (deliberate, moved coherently):** the ENT-11 required literal `chown -R www-data:www-data` was **replaced** (it pinned the contract to the co-tenant-shared account); `config/enterprise_foundation_runtime_hardening.php` `queue_worker.service_user` www-data→`daengtisiams` + marker `User=daengtisiams`/`Group=daengtisiams`; `deploy/systemd/daengtisiams-queue-worker.service` User/Group→`daengtisiams`. **Sibling repins:** `PostEntFoundationRuntimeHardeningTest` (now asserts `User=daengtisiams` + `not User=www-data`) and `DeployRuntimePermissionsScriptTest` (its `toContain('php-fpm')` assertion encoded the pool-scan heuristic — repinned to explicit-authority + forbidden-identity). **Gotcha:** CLAUDE.md records that a prior sprint accidentally dropped that ENT-11 literal and failed CI; here it is changed on purpose with config + both scripts + tests together.

## DEPLOY-HARDEN-1 — Immutable Deployment Entrypoint & Self-Update Safety (2026-08-15)

Branch `feature/deploy-harden-1-immutable-deployment-entrypoint-self-update-safety` (base `feature/sprint-26-phase-26-8-stabilization-closure-go-watch-no-go-report`, baseline INFRA-SEC-RUNTIME-1 GO `acf1e224` / base tip `a3d1723`; do NOT target main). Sprint doc `docs/sprints/deploy-harden-1-immutable-deployment-entrypoint-self-update-safety.md`; runbook `docs/runbooks/vps-deploy-rollback-runbook.md`; rule mirror `.cursor/rules/92-immutable-deployment-entrypoint.mdc`; manifest `.sprint/current.yml` (INFRA_RELEASE). **No migration, no permission, no route, no application runtime change.**

**Root cause.** `scripts/deploy-vps.sh` was executed straight out of the working tree while, halfway through its own body, it ran `git checkout` + `git pull --ff-only`. bash reads a script **incrementally** and keeps a byte offset into the open file, so rewriting those bytes under a running interpreter is undefined behaviour. The same defect existed one indirection removed: after the pull the deploy re-read `bash scripts/harden-secret-permissions.sh` (INFRA-SEC-ENV-1) and `bash scripts/verify-runtime-isolation.sh` (INFRA-SEC-RUNTIME-1) out of the tree it had just rewritten — the two most security-critical gates in the chain reading post-mutation bytes. `rollback-vps.sh` was equally exposed; its `mktemp` staging of the verifier protected the verifier but left the rollback script itself mutable. Two releases were rescued with a manual pre-pull; that workaround is now removed as a prerequisite.

**Invariant locked: `RUNNING_DEPLOY_PROGRAM != MUTABLE_REPOSITORY_FILE`.**

**New execution model.** `deploy-vps-runner.sh start` (unchanged operator interface, VPS-only) → `deploy-vps.sh` hands over before mutating → **new `scripts/deploy-immutable-exec.sh`** (the trusted bootstrap): exclusive `flock` on `/run/daengtisiams-deploy/<role>.lock` → `git fetch` + **pin `TARGET_SHA`** → `git archive TARGET_SHA -- scripts deploy` into a per-run **0700 root-owned** dir under `/run` (fallback `/var/lock`) → overlay the **live** `deploy/runtime-identity.conf` → trust check (owner == deploy uid, restricted mode, no symlink) → run `<snapshot>/scripts/deploy-vps.sh` as a **child** (not `exec`, so the lock fd stays open and the EXIT trap survives) → trap purges the snapshot and **preserves the real exit code**. The deploy then fast-forwards with `git merge --ff-only "$TARGET_SHA"` and verifies `HEAD == TARGET_SHA` twice (after checkout, and as the last gate before `DEPLOY OK`). Post-mutation helpers are invoked as `bash "${DEPLOY_TOOLS_DIR}/scripts/..."`. **Pre-mutation bootstrap chain may still read the working tree** (nothing has mutated yet); everything at/after the first mutation runs from the snapshot.

**Rollback** gets the same lock/pin/snapshot treatment, resolves the operator tag to one exact `ROLLBACK_TARGET_SHA` before mutating, and takes its snapshot from **HEAD (current code)** — never from the older target — so INFRA-SEC-ENV-1 + INFRA-SEC-RUNTIME-1 still run in their modern form. The old `RUNTIME_GUARD_DIR` mktemp staging is gone (superseded).

**Durable rules (mirror `.cursor/rules/92`):** running deploy program is never a mutable repo file · immutable trusted snapshot from a git object · full execution closure in the snapshot · exact-SHA pin before any mutation · moving remote never retargets a running deploy · `HEAD == TARGET_SHA` before `DEPLOY OK` · one deployment critical section at a time (second → exit **75** BUSY before backup/migration/checkout) · lock+snapshot on a root path, never `storage/`/`bootstrap/cache` · advisory lock is authoritative, a lock **file** on disk is not (never delete it to unstick a deploy) · trap cleanup guarded + exit code preserved · backup before migrate absolute · `migrate --force` only · dirty tracked checkout fails closed, never `git reset --hard` · runner runs **on the VPS only** · launcher start ≠ completion · **manual pre-pull is never a prerequisite (reintroducing one is NO-GO)** · production deploys merged authority only · scripts never print a secret.

## STORAGE-PUBLIC-CLINICAL-EVIDENCE-1 — Private Clinical Evidence Remediation (2026-08-23)

Branch `feature/storage-1-object-storage-readiness` (base `feature/sprint-26-phase-26-8-stabilization-closure-go-watch-no-go-report`, baseline `restore-drill-evidence-read-state-1-go` @ `6c66762`; do NOT target main). Sprint doc `docs/sprints/storage-public-clinical-evidence-1.md`; rule mirror `.cursor/rules/121-clinical-evidence-private-storage.mdc`; manifest `.sprint/current.yml` (SECURITY_FIX). **Active clinical-data confidentiality incident, contained then remediated.**

**STORAGE-1 was NOT re-run.** Its GO tag `storage-1-object-storage-readiness-go` @ `d8a9c73` (2026-07-05) is untouched and was not moved; the roadmap still marks STORAGE-1 `completed`. Its object-storage scaffold stays OFF and production stays on local storage — object-storage cutover remains a separate, separately-authorized sprint.

**What was found.** A storage inventory at the base commit found native clinical evidence written to Laravel's `public` disk, which is symlinked into the document root (`public/storage -> storage/app/public`) and therefore served by nginx with **no session, no policy, no branch check**. Proven on production, not inferred: a synthetic 32-byte non-PII probe written into `storage/app/public/handwritings/` was fetched over plain HTTPS with no credentials and returned **HTTP 200, byte-identical**; the probe was then deleted. No patient file was ever retrieved to prove the point. Exposed: **46** RME handwriting images, **8** prescription/doctor-signature canvases, **1** lab attachment (55 artifacts, 3.2 MB). Keys were only weakly unguessable — `handwritings/{branch}/{visit}/handwriting_p{N}_{YmdHis}.png`, whose only entropy is a one-second timestamp, against an unauthenticated endpoint with no rate limit. This violated the project's own shipped **STORAGE-R002** ("never a raw public disk URL"), which had been written for *object* storage and was never enforced for the *local* public disk — so every clinical module shipped after STORAGE-1 (Lab evidence 07-10, SATUSEHAT 07-17, LegacyRme 08-19) inherited the gap silently.

**Containment (first, before any code).** One reversible nginx rule — `location ^~ /storage/ { deny all; }` — on the canonical HTTPS server. Chosen over per-directory rules because all three top-level directories on that disk are clinical, so one rule is both smaller and gap-free. No file mutated. Backup `/etc/nginx/sites-available/asia-dental-lab.bak-storage-incident-20260823-151718`; reversal = delete the marked block + reload. Verified after the graceful reload settled: the path that previously returned 200 returns **403**, all three real artifact categories **403**, all 55 files intact, `/login` + `/health/live` + `/health/ready` **200**.

**Permanent fix.** New `clinical_evidence` disk (local, `visibility: private`, `serve: false`, `throw: true`, root `storage/app/clinical-evidence-private`, deliberately absent from `filesystems.links`). New `App\Support\Storage\ClinicalEvidenceStorage` is the **single storage authority** — call sites ask it for the disk and never name one, so a future writer cannot silently pick a served disk and governance has exactly one symbol to assert against. Write paths repointed: `MedicalRecordHandwritingController`, `RmePrescriptionService::storeCanvas`, `LabOrder\AttachmentService::upload`, `Delivery\PodService`. New authorized read routes `rme.handwritings.image`, `rme.handwriting-pages.image`, `rme.prescriptions.canvas`, `attachments.download`, `deliveries.receiver-signature` — thin controllers mirroring `LabWorkflowEvidenceController@show`: authorize, then stream; the filesystem key is never returned. `AttachmentDownloadController` maps `entity_type` → owning policy **explicitly and fails closed** on an unmapped type. Object keys are **preserved verbatim**, so the migration rewrites **no database column**.

**Migration.** `php artisan clinical-evidence:migrate-public` — `--apply` copies and verifies by SHA-256 with the **source untouched**; `--purge-source` re-verifies then deletes. Nothing is deleted before a byte-identical copy is proven. Each phase writes a manifest (key, size, both checksums, outcome) to `storage/app/clinical-evidence-migration/` as rollback evidence, and verifies every stored DB reference resolves privately (inline data-URI rows counted separately — they never touched the filesystem).

**Governance.** New **STORAGE-R006** — clinical evidence never on a publicly served disk (pinned rule-id assertion in `Storage1GovernanceIntegrationTest` updated R001–R006). New `tests/Feature/Storage/ClinicalEvidencePrivacyTest.php` (20) registered in `config/ci_runner.php` `critical_gate_mandatory_suites` **and** added as the `ClinicalEvidence` token to **both** runner variants of the critical gate — a control CI never selects is not a control. This deliberately broadens that registry beyond monitor-truthfulness; the precedent is earned.

**Gotchas.** (1) A Blade comment `{{-- --}}` inside an `@php` block is parsed as PHP and breaks the template — it cascaded to 39 test failures; always run `php artisan view:cache` after editing Blade. (2) `systemctl reload nginx` is graceful, so a request immediately after reload can be served by an old worker on the old config — the first containment verification produced a false 200 for exactly this reason; re-verify after workers cycle. (3) Grepping only `disk('public')` misses `storeAs($dir, $name, 'public')` — that form hid two writers. (4) `sys_attachments.uploaded_by` is a required FK.

**Print/PDF.** `orderedHandwritingPages(true)` embeds inline base64. `print-body` is shared by the browser print view **and** the dompdf export, and dompdf cannot present a session cookie, so a linked image would export blank — one code path removes that failure class entirely. `RmePdfPrintHardeningTest` now asserts the data URI is present **and** the route URL is absent.
