## REVISION-NEW-VISIT-PATIENT-SEARCH-COMBOBOX-1 — Kunjungan Baru patient selection (2026-08-29)

Branch `revision/new-visit-patient-search-combobox-1` (base `feature/sprint-26-phase-26-8-stabilization-closure-go-watch-no-go-report`, baseline `revision-rme-reports-today-default-1-go` @ `756bc7d`; do NOT target main). Sprint doc `docs/sprints/revision-new-visit-patient-search-combobox-1.md`; rule mirror `.cursor/rules/100-new-visit-patient-search-combobox.mdc`; manifest `.sprint/current.yml` (MODULE_SPRINT). **No migration, no permission, no policy, no route rename.**

**What it replaced.** "Kunjungan Baru" had TWO stacked controls: a `<input type="search">` that only set `option.hidden`, plus a native `<select name="patient_id">` **preloaded with every patient the controller returned** — and each `<option>` label ended with that patient's **phone number**. The controller query was `Patient::with('branch')->orderBy('name')` with `DoctorPatientScopeService::applyPatientScopeForUser`, which returns the query **unchanged for every non-Doctor role** — so Admin Klinik / Kasir / Perawat / Owner / Supervisor RME / Super Admin got every patient in every branch (RME-enabled or not, active or not) serialised into the page. Collapsing to one control was the visible half; removing the estate-wide preload and scoping the search was the substantive half.

**Now.** ONE `<x-patient-combobox>` (hidden `patient_id` is the only submitted value) backed by `GET rme/visits/patient-search` (`rme.visits.patient-search` → `ClinicVisitController::patientSearch`, gated by the ClinicVisit `create` ability). New `App\Modules\Patient\Services\PatientSelectorSearchService` (`MIN_QUERY_LENGTH=2`, `RESULT_LIMIT=15`) → new `PatientRepositoryInterface::searchSelectable()`/`findSelectable()` (the service owns authorization, the repository owns the query; doctor scope passed down as a `Closure`). **Branch scope is delegated to `RmeWorkingBranchScope::branchIdsFor()`** — the same canonical authority `ClinicVisitPolicy` uses: a context-bound role (Admin Klinik/Perawat/Kasir) searches ONLY its active working branch and **fails closed to empty** with no context; governance roles get the active RME-enabled set; Doctors are additionally narrowed by `DoctorPatientScopeService`; legacy `branch_id IS NULL` patients stay selectable; non-RME-branch patients never are. **The endpoint accepts no `branch_id` and no `limit`** — neither can be widened/raised from the query string. LIKE metacharacters escaped with an explicit `ESCAPE '\'` clause (portable PG + SQLite).

**Least disclosure:** the response carries exactly `id`, `name`, `medical_record_number`, `branch_label` — pinned by an **exact key-set assertion**, so phone/WhatsApp/KTP/address/DOB/email cannot reappear silently. (`branch_label` is included on the `CrossBranchPatientLookupService` precedent that classifies it non-sensitive; for an RM-bearing patient it only restates the branch code already inside the Nomor RM.)

**Submit-time boundary (closed a real pre-existing IDOR):** `StoreClinicVisitRequest` validated `patient_id` with `Rule::exists` **and nothing else**, so any authorized user could POST any patient id from any branch. It now re-asserts via `PatientSelectorSearchService::isSelectable()` — deliberately the SAME scope the search uses, so selectable and submittable cannot drift apart. `prepareForValidation` also nulls `patient_id` when `patient_mode === 'new'` (a hidden panel still submits its inputs).

**Browser-only invariants get their own test layer.** The state machine lives in `resources/js/patient-combobox.js` (a plain factory; `app.js` only does `Alpine.data('patientCombobox', ...)`) so it is unit-testable: `tests/js/patient-combobox.test.mjs` via **Node's built-in runner, no new dependency** (`npm run test:js`, 18 tests). It pins (a) typed text is NEVER a selection and any keystroke after a selection clears `patient_id`; (b) a slower earlier response can never overwrite a newer query — monotonic request sequence + AbortController, re-checked after **every** await **including after `response.json()`** (the second suspension point, the one usually forgotten). **Do not move this back inline into `app.js`.**

**Gotchas found:** (1) `_form.blade.php` had a second `<x-patient-search-select>` in an `@else` branch for `$visit !== null` — unreachable dead code (`_form` is only included from `create.blade.php` with `visit => null`; `edit.blade.php` does not include it) referencing a now-absent `$patients`. Removed — it was exactly the "hidden duplicate select" this revision must not leave behind. (2) A test that switched an Admin Klinik's branch mid-day via `rmeMakeAdminClinicActive` correctly **threw** — the DAILY-BRANCH-CONTEXT-LOCK-1 lock owns mid-day moves; the test now proves both halves (unapproved switch refused, then `BranchChangeApprovalService::request()`+`approve()` and the search follows). (3) `PatientFactory` sets no `branch_id`, so existing fixtures are legacy-null and stay selectable — that is why the new submit-time boundary did not break the RME suite.

**Deliberately unchanged:** inactive patients stay selectable ("inactive" ≠ "unauthorized"); `CrossBranchPatientLookupService` untouched and must never become a selection source (it returns no patient id); the legacy `x-patient-search-select` component still serves `resources/views/lab-orders/_form.blade.php` (dental Lab Order — different page, out of scope, carries the same preload+phone shape and deserves its own sprint). Dusk hooks `@patient-search` / `@patient-select` preserved so `tests/Browser/RmeCreateSmokeTest` still asserts the real control.

## BUGFIX-NEW-VISIT-PATIENT-SEARCH-RUNTIME-1 — New Visit patient search survives PostgreSQL (2026-08-29)

Branch `bugfix/new-visit-patient-search-runtime-1` (base `feature/sprint-26-phase-26-8-stabilization-closure-go-watch-no-go-report`, baseline `revision-new-visit-patient-search-combobox-1-go` @ `eba713b`; do NOT target main). Sprint doc `docs/sprints/bugfix-new-visit-patient-search-runtime-1.md`; rule mirror `.cursor/rules/130-raw-sql-driver-parity-and-gate-selection.mdc`; manifest `.sprint/current.yml` (RUNTIME_FIX). **Production regression fix. NO migration, no schema, no permission, no policy, no route, no route rename, no frontend change.**

**The outage.** Every patient search on "Kunjungan Baru" returned HTTP 500 in production; the operator only ever saw the frontend's generic transport message `Gagal mencari pasien. Silakan coba lagi.`, so a total breakdown of patient selection looked like an unhelpful UI. Measured from production logs, not guessed: one `pilot.ERROR` per keystroke on route `rme.visits.patient-search`, `SQLSTATE[HY093]: Invalid parameter number: parameter was not defined`. The request reached the controller, passed authorization and validation, and was correctly branch-scoped (`branch_id in (2)`) — it died in the driver.

**Root cause.** `PatientRepository::searchSelectable()` escaped LIKE metacharacters with a backslash and declared it in SQL: `->whereRaw("LOWER(name) LIKE LOWER(?) ESCAPE '\\'", [$like])`, rendering `ESCAPE '\'`. That is valid SQL and both engines execute it. The fault is one layer up: PDO must rewrite `?` into `$n` before pdo_pgsql can send a statement, and **through PHP 8.3** its parser treats a backslash inside a single-quoted literal as escaping the closing quote — the literal runs on, swallows the placeholders behind it, and PDO binds fewer parameters than the three supplied. Isolated at the PDO layer: **pgsql + PHP 8.3.33 = FAIL (HY093); pgsql + PHP 8.5.4 = OK; sqlite (either) = OK.**

**Why every test was green — three blind spots at once.** (1) **Driver**: pdo_sqlite takes positional `?` natively, so PDO never runs the rewriting parser and the fault is *genuinely absent* there, not merely untested; `phpunit.xml` sets `DB_CONNECTION=sqlite`. (2) **Selection**: `NewVisitPatientSearchComboboxTest` already covered branch scope, IDOR, privacy, bounds and wildcards — and matched **no token** in either NSF-R011 critical filter, so the one failing combination (PostgreSQL 16 on PHP 8.3, which is both the gate and production) was never pointed at it. (3) **Runtime identity**: the VPS default CLI is PHP **8.5.8** — that is the co-tenant `aish-pos`; DaengtisiaMS is served by the `php8.3-fpm` pool `daengtisiams` (`/etc/php/8.3/fpm/pool.d/daengtisiams.conf`), so reproducing from the VPS command line would also have passed.

**Fix, in three parts.** (a) The LIKE escape character is now the private constant `PatientRepository::LIKE_ESCAPE = '!'`, read by both the SQL clause and `escapeLike()` so they cannot drift; the explicit `ESCAPE` clause stays (it is what keeps `%`/`_` literal identically on both engines) and the character escapes itself first. (b) Both patient-search suites are declared in `config/ci_runner.php` `critical_gate_mandatory_suites` **and** selected by a `NewVisitPatientSearch` token in **both** critical-gate variants — declaring without a token fails `CriticalGateSuiteCoverageTest`, a token without a declaration can be dropped silently. (c) New `tests/Feature/RME/NewVisitPatientSearchRuntimeTest.php` replays PDO's own tokenising rule in PHP and asserts placeholder count equals binding count, so the class fails on SQLite and on PHP 8.5 too and can never again hide behind whichever database the suite points at.

**Preserved, explicitly.** No authorization was relaxed to make search work: `RmeWorkingBranchScope` still owns branch scope, the endpoint still accepts no `branch_id`, the daily branch context still owns mid-day moves, `patient_id` is still re-authorized at submit, ceiling 15 / min query 2 / debounce 300 ms unchanged, response still exactly `id`/`name`/`medical_record_number`/`branch_label`. The frontend is untouched — it was correct, and rendering the error state for a real 500 is its job.

**Recorded, not fixed (out of scope):** `patientVisitOptions` lacks a branch check; the dental Lab Order form still exposes phone via the retired `x-patient-search-select`; `CrossBranchPatientLookupService` and `LegacyRmePatientResolutionAuditService` escape with a backslash but emit no `ESCAPE` clause (cannot hit this fault; their escaping is a no-op on SQLite); `ReportingSummaryGovernanceService` has `ESCAPE '\'` in four statements that carry **zero bindings**, so there are no placeholders to miscount.

**Durable rules (mirror 130):** a SQL string literal must never close on a backslash · SQLite green is not PostgreSQL green · production's PHP is the FPM pool's version, not the CLI default · a suite no filter token matches is not a control · a successful empty result is not an error (`SUCCESS_WITH_RESULTS` / `SUCCESS_EMPTY_RESULTS` / `SEARCH_RUNTIME_ERROR` stay distinct).

## REVISION-NEW-VISIT-GLOBAL-PATIENT-LOOKUP-1 — New Visit patient lookup is global patient identity (2026-08-30)

Branch `revision/new-visit-global-patient-lookup-1` (base `feature/sprint-26-phase-26-8-stabilization-closure-go-watch-no-go-report`, baseline `bugfix-new-visit-patient-search-runtime-1-go` @ `31a88b8c`; do NOT target main). Sprint doc `docs/sprints/revision-new-visit-global-patient-lookup-1.md`; rule mirror `.cursor/rules/101-new-visit-global-patient-identity-lookup.mdc`; manifest `.sprint/current.yml` (MODULE_SPRINT). **Deliberate business-rule revision, not a bug fix. NO migration, no schema, no column, no index, no route, no route rename, no permission, no policy, no role change.**

**THE CANONICAL RULE THIS SPRINT ESTABLISHES — GLOBAL PATIENT IDENTITY FOUNDATION.** Authorized New Visit registration may search the global patient registry by patient **name** or **Nomor RM**. Patient identity lookup is global for registration, but **clinical history authorization remains independently scoped**. Search may disclose only minimum registration identity. Selecting a patient from another branch **never** changes the operator's `DailyBranchContext`. The new `ClinicVisit` branch comes from the operator's authorized work context — **not** from the patient's RM origin branch and **not** from a request `branch_id`. A cross-branch patient selection **reuses the existing patient master row**: it must not mutate the patient's RM and must not create a duplicate patient.

```
PATIENT IDENTITY  !=  VISIT BRANCH AUTHORITY
```

**And the domain distinction that must never be conflated:** for **LEGACY RME**, the RM branch code may determine the Legacy evidence branch; for a **NATIVE NEW VISIT**, `DailyBranchContext` determines the visit branch. Different domains, different rules.

**What changed, precisely.** One method: `PatientSelectorSearchService::authorizedBranchIds()` now returns `BranchService::rmeEnabledIds()` (plus the repository's existing legacy `branch_id IS NULL` admission) instead of `RmeWorkingBranchScope::branchIdsFor()`. That service is already registration-specific — the search endpoint, the submit-time `patient_id` re-authorization (`StoreClinicVisitRequest::validateExistingPatientSelectable`) and the create-page prefill all resolve through it — so **search selectability == submit selectability** structurally, not by convention. No `Patient::all()`, no preload, no new god-service.

**Three deliberate design calls, each defensible and each tested.** (1) **"The registry" = active + RME-enabled branches, not every `mst_patients` row.** That is exactly what a governance role (Owner / Supervisor RME / Super Admin) already reads; going wider would newly expose MAIN, disabled and non-RME branches that *no* role sees and where no visit may be registered. (2) **The fail-closed gate survived.** A context-bound operator (Admin Klinik / Perawat / Kasir) with **no valid working context** still reads nothing — global means "any branch's patient", not "no authority required"; someone not working anywhere cannot register anywhere. This also stops the enumeration surface widening to unattached accounts, at zero cost to the requirement. (3) **The doctor clinical scope was left alone.** A Doctor holds `manage_clinic_visits` and is a registration actor, but `DoctorPatientScopeService` still narrows them to their own RM scope — that is a CLINICAL scope, not a branch scope, and widening it would be exactly the identity-vs-clinical confusion this sprint exists to prevent.

**`RmeWorkingBranchScope` was NOT globally relaxed.** It remains the canonical working-branch authority for the visit list, patient queue, RME reports, cashier and receivables. Only this one registration identity lookup is global. Do not relax the scope service itself to satisfy a lookup requirement.

**Visit branch authority — unchanged, now pinned by tests.** For a context-bound operator `StoreClinicVisitRequest::prepareForValidation()` already overwrites `branch_id` with the daily context before validation runs, and `ClinicVisitService::resolveBranchId()` re-checks it against the active RME set. This sprint adds no behaviour there — it adds the tests that make the behaviour impossible to lose, because a widened lookup is precisely the change that would make losing it plausible. Governance roles are not context-bound by design and still pick the branch on the form; that selector is their authorized work context.

**Preserved verbatim:** response keys exactly `id`/`name`/`medical_record_number`/`branch_label` (never phone, WhatsApp, KTP/NIK, address, DOB, email, occupation, or anything clinical — the wider scope makes this ceiling *more* important); `MIN_QUERY_LENGTH` 2; `RESULT_LIMIT` 15; debounce 300 ms; monotonic-sequence + AbortController stale-response safety; endpoint accepts no `branch_id` and no `limit`; `LIKE_ESCAPE = '!'` (never a backslash — see BUGFIX-NEW-VISIT-PATIENT-SEARCH-RUNTIME-1) and the placeholder-parity guard suite. Frontend churn is one line of helper copy: the combobox already rendered `branch_label`, which is **disambiguation only and never authority**.

**CI gate.** `NewVisitGlobalPatientLookupTest` matched **no** token in either critical filter — the same blind spot that let the predecessor outage ship. It is now declared in `config/ci_runner.php` `critical_gate_mandatory_suites` and selected by a `NewVisitGlobalPatientLookup` token in **both** gate variants.

**Rules synchronised, no contradiction left standing:** `.cursor/rules/100-new-visit-patient-search-combobox.mdc` section 3 (branch-scoped lookup) is explicitly marked **SUPERSEDED** and re-pointed at the new rule 101; section 8 re-worded. Rule 100's other nine sections stay in force.

**Evidence.** TDD observed — the new suite failed **16 of 29** before any production code changed. `NewVisitGlobalPatientLookupTest` 29 passed; combobox+runtime suites 42 passed; **combined 71 passed / 305 assertions on PostgreSQL 16.14 + PHP 8.3.33** (the pinned CI runtime image, production's FPM major.minor, driver asserted as `pgsql` rather than assumed — SQLite green is not PostgreSQL green); regression 639 passed / 9 skipped; `tests/js/patient-combobox.test.mjs` 19 passed; Dusk `NewVisitGlobalPatientLookupBrowserTest` (new, a genuinely context-bound Admin Klinik — a Super Admin would prove nothing, it already had estate-wide scope) 2 passed + `NewVisitPatientSearchBrowserTest` 4 passed. **Mutation: 15 attempted, 15 killed, 0 real survivors** (revert by file copy, never `git checkout --`, because the sprint adds untracked test files).

**Recorded, NOT fixed here (and this sprint is explicitly not their justification):** `ClinicVisitController::patientVisitOptions` lacks a branch check — a test in the new suite asserts cross-branch **visit detail** is still refused; the dental Lab Order form still exposes phone via the retired `x-patient-search-select` (a different component that does not use this service); `CrossBranchPatientLookupService` and `LegacyRmePatientResolutionAuditService` escape LIKE with a backslash but emit no `ESCAPE` clause.

## FEATURE-PATIENT-DUPLICATE-RESOLUTION-MERGE-1 — Duplikasi Pasien (2026-10-07)

Branch `feature/patient-duplicate-resolution-merge-1` (base `feature/sprint-26-phase-26-8-stabilization-closure-go-watch-no-go-report` @ `1fdfe3f6`; do NOT target main). **New bounded context `App\Modules\PatientMerge`** + sidebar group **Duplikasi Pasien** (Dashboard, Deteksi Duplikat, Pilih Pasien Manual, Pengajuan Merge, Review & Approval, Riwayat Merge, RM Alias) under `/rme/patient-merge` (`patient-merge.*`, every `{patientMergeCase}` constrained `whereUuid`). **Migrations (additive only):** `2026_10_07_100001` (`trx_patient_merge_cases`, `trx_patient_merge_field_resolutions`, `mst_patient_rm_aliases`) and `2026_10_07_100002` (nullable `merged_into_patient_id`/`merged_at`/`merged_by`/`merge_case_id` on `mst_patients` + indexes). **Permissions:** `view_patient_duplicate_resolution`, `request_patient_merge` (Admin Klinik, Front Office, Supervisor RME), `approve_patient_merge` (Supervisor RME); Super Admin via `Gate::before`. Deploy: `PermissionSeeder` → `RoleSeeder` → `permission:cache-reset`.

**A merge reassigns OWNERSHIP, never content.** `PatientOwnedRecordRegistry` lists every patient FK (21 REASSIGN tables + PRESERVE), checked against the LIVE schema every time (`OWNERSHIP_REGISTRY_INCOMPLETE` blocks). One transaction: case lock → legacy slot advisory locks (both types, both patients, sorted) → patient rows `FOR UPDATE` → blockers + identity fingerprint re-checked → source KTP released → final identity on canonical → colliding doctor assignments closed (notes appended, originals kept) → registry reassignment → aliases → source marked merged (never deleted) → conservation proven over the two patients → audit. Any throw rolls everything back; refusals AND failures are audited after the rollback.

**Blockers (fail closed, never auto-resolved):** missing/same/deleted/merged patient, canonical not chosen, unresolved critical identity conflict, final NIK held by a third patient (never named), in-flight legacy import, two active legacy archives of one type, **live encounter on either patient** (`ACTIVE_ENCOUNTER`), **SATUSEHAT identifier on the source** (non-FK reference), **legacy date rule on the combined timeline**, unregistered patient FK, identity changed since submission.

**Maker-checker in the service** (Super Admin bypasses policies): only the requester resolves/submits/withdraws; every author (requester, submitter, field resolver) is refused approval and rejection. A/B values are re-derived at submission. **Reversal** is SAFE only when provably nothing happened since (id high-water mark recorded inside the merge, moved rows unchanged, child rows via parents, parent-reference probe, no deleted patient, canonical identity unchanged); otherwise SUPERVISED; a different reviewer executes it.

**Integration points:** visit registration re-reads the patient `FOR SHARE`; legacy RME/odontogram intake re-reads it after its slot lock; `PatientService` update/delete/activate re-check under lock; patient selector excludes merged patients and resolves old RM via alias; merged patient edit / RME workspace redirect to canonical (RME redirect only when the actor can open the target, else 404); legacy patient batch rollback refuses merge involvement; registration (patients + New Visit) warns on strong duplicates only, requires a reason to continue, audited, and discloses only name/RM/branch outside the actor's scope.
