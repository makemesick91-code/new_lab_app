## RME Module (Sprint 20)

**Modules:** `ClinicVisit`, `MedicalRecord`, `Odontogram`, `RmeInvoice` under `app/Modules/`.

**Routes:** `rme.*` prefix in `routes/web.php`.

**Workflow:** Admin creates visit → Doctor odontogram + handwriting RME → finalize →
`cashier_pending` → Cashier invoice + full payment → `completed` → print receipt.

**Visit statuses:** `registered`, `waiting`, `in_progress`, `cashier_pending`, `completed`, `cancelled`.

**Invoice statuses:** `DRAFT`, `UNPAID`, `PAID`, `VOID`. **[SUPERSEDED 2026-10-16 by AUDIT-RME-BILLING-CORRECTION-PAYMENT-REFUND-FOUNDATION-1 / rule 188: the authoritative set is `DRAFT/UNPAID/PARTIAL/PAID/VOID`; creation writes `UNPAID` directly and no application path writes `DRAFT` or `VOID`.]**

**Rules:**
- Handwriting RM is the **primary doctor-facing clinical input**; SOAP fields are optional legacy structured fields hidden from doctor UI.
- Handwriting PNG **mandatory** before RME finalization; immutable after finalize.
- Initial service is triage-only — **no billing**.
- Cashier billing requires finalized RME + `cashier_pending` visit (`manage_rme_billing`).
- **Full payment only** in pilot — partial/cicilan deferred. **[SUPERSEDED: partial payments are accepted and complete the visit — see Hotfix RME Partial Payment Completes Visit; rule 188 §3.]**
- Print via browser `window.print()` — no server PDF. **[SUPERSEDED: a dompdf receipt route `rme.cashier.receipt.pdf` exists; receipts are rendered live with no snapshot — rule 188 §5.]**

**Permissions:** `view_clinic_visits`, `manage_clinic_visits`, `manage_rme_billing`.

**Pilot doc:** `docs/sprint_20_rme_limited_pilot_summary.md`

**Pilot master data import:** use `php artisan rme:import-pilot-backup` (see `docs/rme_pilot_backup_import_guide.md`). Never restore backup SQL directly over the Sprint 20 database.

**UI:** All RME views use TailAdmin components (`x-ui.card`, `x-ui.table`, `x-ui.badge`, `x-ui.button`, `x-settings-shell`). UI modernization merged into `feature/sprint-20-rme-core` (merge commit `8246008`, tag `sprint-20-rme-ui-modernization-merged`).

## LEGACY-RME-DATE-TZ-1 — Canonical Clinical Timezone & Date-Boundary Correctness (2026-08-15)

Branch `feature/legacy-rme-date-tz-1-canonical-clinical-timezone-date-boundary-correctness` (base `feature/sprint-26-phase-26-8-stabilization-closure-go-watch-no-go-report`, BASE_SHA `a258586`; do NOT target main). Sprint doc `docs/sprints/legacy-rme-date-tz-1-canonical-clinical-timezone-date-boundary.md`; runbook `docs/runbooks/clinical-timezone-date-boundary-runbook.md`; rule mirror `.cursor/rules/92-canonical-clinical-timezone-date-boundary.mdc`; manifest `.sprint/current.yml` (RUNTIME_FIX). **No migration, no data backfill, no permission, no route, no schema change; ledger/RME/inventory workflows untouched; KTP/NIK never rendered; Legacy archive stays OFF.**

**Root cause (verified, not inferred).** `config/app.php` hard-codes `'timezone' => 'UTC'` and never reads `APP_TIMEZONE`; the legacy archive declared its clinical calendar as `env('LEGACY_RME_CLINICAL_TIMEZONE', env('APP_TIMEZONE', 'UTC'))`; neither variable is set in production and `.env.example` carried no timezone key at all — so the clinical calendar silently resolved to **UTC**. Two services repeated the same inline fallback (`LegacyRmeDateRuleService::timezone()`, `LegacyRmeMigrationQuotaService::today()`). Because `Asia/Makassar` is UTC+08:00, `2026-08-13T16:00:00Z == 2026-08-14 00:00:00` in the clinic: for the eight hours between 16:00Z and midnight Z the two calendars name different days, so the rule `latest_rme_date < today` gave the **same document two different answers depending only on the hour of submission**. A second, quieter defect: `config/satusehat.php` already declared `clinic_timezone` defaulting to `Asia/Makassar`, so the codebase carried **two clinical-timezone authorities that disagreed in production**.

**Two semantic domains — permanently separate.** TECHNICAL INSTANT (`2026-08-13T16:00:00Z`; `created_at`/`updated_at`/queue/`sys_audit_logs`/deploy logs/telemetry) keeps the existing **UTC** architecture — `config/app.php` stays `'UTC'` **on purpose** and **no timestamp was converted**. CLINICAL CALENDAR DATE (`2026-08-14`) is `Asia/Makassar` and is read **only** through `App\Support\Clinical\ClinicalClock`. A UTC process default beside a WITA clinical calendar is the CORRECT posture, not a finding.

**Canonical authority (one literal, one reader).** New `config/clinical.php` → `'timezone' => env('CLINICAL_TIMEZONE', ClinicalTimezone::DEFAULT)`; new `App\Support\Clinical\ClinicalTimezone` (`DEFAULT = 'Asia/Makassar'` — the ONLY literal; `isValid()` matches the platform's IANA identifier list so `WITA`/`UTC+8`/`GMT+8`/`+08:00` and the real typo `Asia/Makasar` are all **rejected**, not silently accepted as a fixed offset); new `App\Support\Clinical\ClinicalClock` (`timezone()`/`today()`/`now()`/`toClinicalDate()`/`todayString()`/`inspect()`); new `InvalidClinicalTimezoneException`. **`config/legacy_rme.php` `dates.clinical_timezone` was REMOVED** (comment records why it must never come back) and `config/satusehat.php` `clinic_timezone` now derives its default from the same constant (effective value unchanged) — two config files that can disagree about what day it is are the defect, not the fix. `LegacyRmeDateRuleService` + `LegacyRmeMigrationQuotaService` inject the clock and their inline UTC fallbacks are gone; `LegacyRmeMigrationQuotaFactory` uses it so fixtures land in the bucket the gate reads.

Requiring the signature first made the workflow **circular** — the form could not be completed until the finding existed, and the finding could not be recorded until the form was signed.

**The change is one condition in one method.** `RmeVisitConsentService::assertOdontogramAuthoringAllowed()` went from four checks to three: (1) the patient has a single current `in_progress` encounter (ambiguity fails closed), (2) the actor may work on it (branch + `DoctorPatientScopeService`; unresolvable actor fails closed), (3) the chart IS that encounter's own chart. The `hasValidConsent()` check is removed, and its absence is **stated in the method** so it never reads as an oversight. Small because CORRECTIVE-03 had centralised the rule: all three write paths (`saveForVisit`/`updatePlaceholder`/`finalize`) already funnelled through that assertion and the page already derived its controls from `canAuthorOdontogramFor()`, which delegates to it — there was no second check anywhere to hunt down. **Do not add one.**

**Odontogram `finalize()` is also permitted pre-consent** — it is a chart-level lifecycle act (Sprint 59: a finalized chart stays revisable) and leaves the visit `in_progress`. It shares the one assertion; splitting it out would create a second divergent consent rule. "Selesai Pemeriksaan" is the *workflow* transition and stays gated in `ClinicVisitService::transitionStatus()`.

**Unchanged and re-pinned:** RME blocked pre-consent (also after charting — charting is never an implicit consent); finish blocked pre-consent even with a complete chart; charting before "Mulai Pemeriksaan" refused (`registered`/`waiting`) and after it (`cashier_pending`/`completed`/`cancelled`); non-Doctor and other-Doctor refused; historical native charts and published Legacy Odontograms permanently immutable; another visit's consent never unlocks the live RME; a save creates/signs no consent and advances no status; pre-consent charting survives the later signature (same row, same teeth, no duplicate).

**UI.** The odontogram page's warning ("...belum dapat diubah. Pasien harus menandatangani form consent sebelum dokter dapat mencatat atau mengubah odontogram") was **false** after this change and is replaced by a reminder of what is still true: charting is available; the RME and Selesai Pemeriksaan remain locked until the signature. Controller `$odontogramConsentRequired` → `$consentPendingForRme`. Operationally load-bearing — a doctor can now finish the whole chart without ever meeting the gate and would otherwise first learn the visit is stuck when trying to finish it.

**Superseded:** the CORRECTIVE-03 clause "consent gates the active odontogram", corrected in place in `.cursor/rules/109-rme-exam-consent-odontogram-history.mdc` (§0 diagram, §2 bullet, §2c coverage, §4 wording); rule 134 is authoritative where the two disagree. Everything else in rule 109 stands.

**Tests:** new `tests/Feature/RME/RmeConsentOdontogramPreConsentEditTest.php` (31) — written first; **17 failed / 14 passed** against unmodified source, the 14 being every guard-preservation case. Four cases plus the read-only-notice case in `RmeExamConsentCorrective3Test.php` were **revised, not deleted**, each carrying a `REVISED by` note naming what it used to assert. ## BUGFIX-RME-PRECONSENT-FIRST-PAGE-UI-GATE-1 — the empty state stopped offering a create the server refuses (2026-09-02)

Branch `bugfix/rme-preconsent-first-page-ui-gate-1` (base `feature/sprint-26-phase-26-8-stabilization-closure-go-watch-no-go-report`, baseline `revision-rme-consent-odontogram-preconsent-edit-1-go` @ `2c9ec15`; do NOT target main). Sprint doc `docs/sprints/bugfix-rme-preconsent-first-page-ui-gate-1.md`; rule mirror `.cursor/rules/135-rme-authoring-ui-capability-mirror.mdc`. **No migration, no route, no permission, no policy, no schema change. The backend gate was NOT touched — it was already correct.**

**The bug.** Doctor + `in_progress` + consent UNSIGNED + patient with **no RM sheet** was offered an actionable **"Buat Halaman RM Pertama"**, and the server refused the create when they pressed it: `UI = ALLOW`, `BACKEND = DENY`. Reproduced before any change — the new suite's red baseline was 11 failed / 11 passed, and *every* failure was a UI-capability assertion while *every* backend-denial and foundation-preservation assertion already passed. That split is the diagnosis.

**Root cause — a permission check standing in for a capability check.** `MedicalRecordController::show()` renders two workspaces from one method, and they consulted two different authorities for one act. The POPULATED workspace resolved `canAuthorRme`/`addSheetConsentRequired` from `RmeVisitConsentService::canAuthorRmeForPatient()`. The EMPTY workspace resolved `canEdit` from `can('create', [MedicalRecord::class, $workspaceVisit])` — and `MedicalRecordPolicy::create()` checks only `manage_clinic_visits` + RME-enabled branch + `DoctorPatientScopeService::authorizeVisitAccess()`. It carries **no consent condition, correctly**: consent is not a permission, it is a property of the encounter. Meanwhile `MedicalRecordService::createDraft()` asserts `assertRmeAuthoringAllowedForPatient()` (single current encounter · `in_progress` · actor may work on it · valid consent for THAT encounter).

**The fix — the empty state joins the rule that already existed.** No new predicate, and the same key the sheet-add control already uses: the controller now also passes `addSheetConsentRequired` = `! canAuthorRmeForPatient($patientId, $user)` and `activeEncounter`; `resources/views/rme/visits/medical-record/empty.blade.php` renders from them, mirroring the populated workspace — a `warning` alert naming the real reason (`Belum ada pemeriksaan yang berjalan` / `Persetujuan Tindakan Medis belum ditandatangani` + "Pilih Form Consent" link) and the CTA as a **disabled button**, never a live `<form>` at the store route. Disabled rather than hidden follows `rm-sheet-nav.blade.php`'s convention for the identical act: the doctor stays oriented instead of discovering the lock by pressing.

**Durable rule (mirror `.cursor/rules/135`, cross-linked both ways with rule 134):** the active RME authoring UI must mirror the server RME authoring capability; **a permission check is not a capability check** — any control whose act is gated by encounter state, consent or workflow status must consult the capability, not only the permission; UI visibility is never the security boundary; **never re-derive the consent rule in Blade** (a template writing its own `$visit->consent && …` creates a second rule that drifts — exactly this bug); and when UI and backend disagree the resolution is always **UI DENY + BACKEND DENY**, never a relaxed server.

**Explicitly unchanged and re-pinned by this sprint's own suite:** the odontogram stays **editable** pre-consent (REVISION-…-PRECONSENT-EDIT-1 — blocking the record must never drag the chart down with it), "Selesai Pemeriksaan" stays refused pre-consent, before-start refused, other-Doctor and non-Doctor refused, terminal visits closed (a `cancelled` visit has no workspace at all — it is not an eligible RM anchor, so the page 404s before any capability question), another visit's / another patient's consent never unlocks the control, and a forged `source_visit_id` never becomes an authority.

**Superseded:** `tests/Browser/OdontogramPreConsentEditBrowserTest.php` step 4 used to *press* the button and watch the server refuse, with a note recording that it "is gated on the manage permission only, not on consent". That note described this bug; the step now asserts the disabled control and the absent form, keeping its original claim intact.

**CI wiring is double, deliberately:** token `RmePreConsentFirstPageUiGate` in **both** critical-gate filter variants, **and** the file declared in `config/ci_runner.php` `critical_gate_mandatory_suites` (STORAGE-PUBLIC-CLINICAL-EVIDENCE-1 precedent — the mismatch was live in production, nothing in CI asserted the two authorities agreed, and the likely regression produces no error, no exception and no log line, only a control that fails when pressed). The declaration is what makes the token unremovable: `SelfHostedRunnerScanner` fails the gate if a declared file is selected by no token in every variant.

**Tests:** new `tests/Feature/RME/RmePreConsentFirstPageUiGateTest.php` (22) — green on SQLite **and** PostgreSQL 16 (the production driver); new `tests/Browser/RmePreConsentFirstPageBrowserTest.php` (2 Chrome journeys against PG16) proving "not actionable" by asking Selenium whether the element is enabled rather than grepping a label — a disabled button still reads "Buat Halaman RM Pertama", so the label is not the signal, the submittable form is.
